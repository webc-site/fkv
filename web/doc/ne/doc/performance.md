# प्रदर्शन

`fkv_bench` निश्चित कुञ्जी ठाउँमा परीक्षण लेख्नुहोस्, पढ्नुहोस्, र स्क्यान लोड गर्नुहोस्।

```bash
cargo run --release -p fkv_bench -- \
  --workload write-read --rows 20000 --batch-size 100
```

सूचकहरूले थ्रुपुट, प्रत्येक चरणमा विलम्बता, र शिखर RSS समावेश गर्दछ। रिलीज कार्यप्रवाह रिलीज x86_64 /
`fkv_bench` aarch64 को लागि बाइनरी।

## RocksDB/fjall सँग थ्री-वे म्याचअप

`crate/perf/fkv_compare` एउटै स्टेज ड्राइभर र एउटै कुञ्जी इन्कोडिङ प्रयोग गर्नुहोस् (अन्तमा 8-बाइट ठूलो-एन्डियन सबस्क्रिप्ट,
शब्दकोश क्रम सबस्क्रिप्ट अर्डर संग संगत छ) परीक्षण fkv, RocksDB, fjall: RocksDB पारित
`crate/perf/fkv_compare/cpp/rocksdb_ffi.cpp` कम्पाइल गरिएको साझा पुस्तकालय dlopen (उही C) सँग लोड गरिएको छ
ABI, Rust बिल्डले RocksDB सँग लिङ्क गर्दैन), fjall ले `fjall 3` सीधा प्रयोग गर्दछ। तीन इन्जिन मध्ये प्रत्येक एक पुस्तकालय खोल्छ।
चरणहरूको क्रममा एउटै पुस्तकालयमा अग्रिम: बल्क लोडले डाटा सिर्जना गर्दछ, र त्यसपछि लेन / पोइन्ट पढाइ / दायरा पढाइ /
मेटाउने सबैले समान डेटालाई असर गर्छ।

```bash
cargo build --release -p fkv_compare
bash scripts/perf/build_rocksdb_ffi.sh # यदि RocksDB छैन भने तेस्रो स्तम्भ छोड्नुहोस्
./target/release/fkv_compare \
  --rows 25000000 --bulk-rows 25000000 --cache-bytes 268435456 \
  --readers 1,4,8,16,32 --workdir /tmp/fkv-compare \
  --rocksdb-lib target/perf/librocksdb_bench_ffi.so \
  --json /tmp/fkv-compare.json
```

होमपेज म्याट्रिक्सका लागि नम्बरहरू केवल एक ट्रेसेबल रनबाट आउन सक्छ:

```bash
python3 scripts/perf/fkv_compare_to_js.py \
  --json /tmp/fkv-compare.json --perf-js web/src/conf/perf.js \
  --मेसिन "..." --स्रोत "CI रन <id>"
```

GitHub कार्यहरू '`perf.yml` ले ठ्याक्कै यो गर्छ (स्थापना गर्नुहोस् `librocksdb-dev`, प्रोग्राम एडाप्टरहरू, चलाउनुहोस्
25M पङ्क्ति म्याट्रिक्स, आर्टिफ्याक्ट अपलोड गर्नुहोस्, र पृष्ठलाई सीधै ब्याकफिल गर्नुहोस् जब `backfill=true`)।

### क्षमता

- **डेटा/क्यास अनुपात**: २५,०००,००० पङ्क्तिहरू × ११६ बी ≈ २७६६ एमआईबी डाटा, २५६ एमआईबी क्यास प्रति इन्जिन,
  ≈ 11:1, 97 GiB डाटा/6 GiB क्यास (≈ 16:1) को RocksDB को आधिकारिक समीक्षासँग पङ्क्तिबद्ध।
- **क्यासको समान मात्रा**: fkv को पृष्ठ क्यास (सूचकांक/डेटा समान पूल), RocksDB को ब्लक क्यास
  (`cache_index_and_filter_blocks=true`, ब्लक साइज ४ KiB), fjall को आफ्नै ब्लक क्यास
  बजेटहरू सबै बाइटहरूको समान संख्यामा सेट गरिएका छन्।
- **पर्सिस्टेन्स क्यालिबर (तुलना स्तम्भले RocksDB पूर्वनिर्धारित कन्फिगरेसन प्रयोग गर्दछ, पङ्क्तिबद्धता बिना)**: fkv 1×डेटा पृष्ठ + प्रति ब्याच
  1×manifest `fdatasync` (Isomorphic to SyncData + AppendManifest of C++ EloqStore,
  न त बन्द स्विच छ); RocksDB स्तम्भले **पूर्वनिर्धारित कन्फिगरेसन** प्रयोग गर्दछ (WAL on, `WriteOptions.sync=false`,
  कुनै क्रमिक fsync छैन), fjall ले पनि पूर्वनिर्धारित प्रयोग गर्दछ (`PersistMode::Buffer`)। त्यसैले लेखन चरण (एकल लेखन /
  ब्याच राइटहरू बीचको भिन्नता) ** दृढता बल भिन्नता** हो, कार्यान्वयन भिन्नता होइन, जुन पृष्ठमा नम्बर सहित उल्लेख गरिनुपर्छ।
  यदि तपाइँ "उही सिङ्क्रोनाइजेसन बल अन्तर्गत को छिटो छ" को विश्लेषण गर्न चाहनुहुन्छ भने, `--align-fsync` थप्नुहोस् (sinc=true सँग RocksDB खोल्नुहोस्,
  fjall SyncAll प्रयोग गर्दछ), यो विकल्प बाह्य रूपमा प्रकाशित matrices को लागि प्रयोग गरिएको छैन।
- **दुई fkv ड्राइभरहरू**: `--fkv-driver store` (पूर्वनिर्धारित, सीधा एकल `Store` प्रक्रिया भित्र जडान, र
  RocksDB / fjall पनि पुस्तकालय कलहरू हुन्) र `--fkv-driver runtime` (डिप्लोइमेन्ट मोड: एक प्रक्रिया
  `--fkv-shards` शार्ड थ्रेडहरू, अनुरोधहरू कुञ्जीद्वारा रुट गरिएका छन्, C++ EloqStore को सार्वजनिक पठन र लेखनसँग पङ्क्तिबद्ध छन्।
  इन्टरफेस)। पछिल्लोको प्रत्येक अनुरोधलाई कतार + क्रस-थ्रेड वेक-अप, नेटिभ (macOS, फाइल IO थ्रेड पूल मार्फत जान्छ) मार्फत जान आवश्यक छ।
  पढ्ने समय लगभग 20 µs/समय हो, जुन प्रक्रियामा प्रत्यक्ष जडान भन्दा ढिलो परिमाणको क्रम हो; लिनक्स/io_uring मा धेरै सस्तो, तर
  अझै एक छलांग। पृष्ठ म्याट्रिक्सले स्टोर क्यालिबर प्रयोग गर्दछ, र रनटाइम क्यालिबर "डिप्लोइमेन्ट फारम बनाम C++" को लागि प्रयोग गरिन्छ।
  "सार्वजनिक इन्टरफेस" को तुलना (fkv रनटाइम एकल-थ्रेड पढाइ लगभग 50 kops/s, C++ EloqStore FFI एकल-थ्रेड हो।
  शार्ड लगभग 21 kps/s)।
- **समवर्ती क्यालिबर पढ्नुहोस्**: fkv साइड थ्रेड नम्बर = `min(readers, --read-max-concurrency)`, पूर्वनिर्धारित
  माथिल्लो सीमा 4 हो (मूल्याङ्कन मेसिन vCPU सँग पङ्क्तिबद्ध), ** होइन ** "प्रति पाठक एक थ्रेड" - नाघेको स्तरले लाम मात्र बढाउँछ;
  क्यास प्रति थ्रेड = 256 MiB / थ्रेडहरूको संख्या (कुल रकम निश्चित छ, पाठकहरूसँग काटिएको छैन), र प्रयोग गरियो
  `FuturesUnordered` फ्लाईमा `--read-window` (पूर्वनिर्धारित १६) अनुरोधहरू राख्नुहोस्। RocksDB पक्ष हो
  `readers` प्रत्येक `std::thread` एकैसाथ पढ्छ; fjall साइडमा एकल-थ्रेडेड लुप (पाठक गियर बेवास्ता गर्दै,
  केवल सन्दर्भ स्तम्भको रूपमा)। `--no-fkv-read-threads` "एकल रनटाइममा इन्टरलीभ एन एसिंक्रोनस चेन" मा फिर्ता पतन हुन सक्छ।
  त्यो पाइपलाइनको गहिराइ हो, कन्कर्रेन्सी होइन, र इन्जिनहरूमा तुलना गर्न मिल्दैन।
- **len()**: तीन इन्जिन मध्ये कुनै पनि O(1) काउन्टिङ इन्टरफेस छैन। यो रेखा पूर्ण तालिका गणना दर हो, O(1) लुकअप होइन।
