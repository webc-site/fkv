# કામગીરી

`fkv_bench` નિયત કી સ્પેસ પર લોડ લખવા, વાંચવા અને સ્કેન કરવાનું પરીક્ષણ કરો.

```bash
cargo run --release -p fkv_bench -- \
  --workload write-read --rows 20000 --batch-size 100
```

સૂચકાંકોમાં થ્રુપુટ, દરેક તબક્કે લેટન્સી અને પીક RSSનો સમાવેશ થાય છે. વર્કફ્લો રિલીઝ x86_64 /
aarch64 માટે `fkv_bench` બાઈનરી.

## RocksDB/fjall સાથે થ્રી-વે મેચઅપ

`crate/perf/fkv_compare` સમાન સ્ટેજ ડ્રાઇવર અને સમાન કી એન્કોડિંગનો ઉપયોગ કરો (અંતમાં 8-બાઇટ મોટી-એન્ડિયન સબસ્ક્રિપ્ટ,
ડિક્શનરી ઓર્ડર સબસ્ક્રિપ્ટ ઓર્ડર સાથે સુસંગત છે) ટેસ્ટ fkv, RocksDB, fjall: RocksDB પાસ
`crate/perf/fkv_compare/cpp/rocksdb_ffi.cpp` સંકલિત શેર કરેલ લાઇબ્રેરી dlopen (સમાન C
ABI, રસ્ટ બિલ્ડ RocksDB સાથે લિંક કરતું નથી), fjall સીધો `fjall 3` ઉપયોગ કરે છે. ત્રણ એન્જિનમાંથી દરેક એક લાઇબ્રેરી ખોલે છે.
તબક્કાના ક્રમમાં સમાન લાઇબ્રેરી પર આગળ વધો: બલ્ક લોડ ડેટા બનાવે છે, અને પછી લેન / પોઇન્ટ રીડિંગ / રેન્જ રીડિંગ /
કાઢી નાખવાથી બધા સમાન ડેટાને અસર કરે છે.

```bash
cargo build --release -p fkv_compare
bash scripts/perf/build_rocksdb_ffi.sh # જો કોઈ RocksDB ન હોય તો ત્રીજી કૉલમ છોડો
./target/release/fkv_compare \
  --rows 25000000 --bulk-rows 25000000 --cache-bytes 268435456 \
  --readers 1,4,8,16,32 --workdir /tmp/fkv-compare \
  --rocksdb-lib target/perf/librocksdb_bench_ffi.so \
  --json /tmp/fkv-compare.json
```

હોમપેજ મેટ્રિક્સ માટેના નંબરો માત્ર એક શોધી શકાય તેવા રનમાંથી આવી શકે છે:

```bash
python3 scripts/perf/fkv_compare_to_js.py \
  --json /tmp/fkv-compare.json --perf-js web/src/conf/perf.js \
  --મશીન "..." -- સ્ત્રોત "CI રન <id>"
```

GitHub ક્રિયાઓ '`perf.yml` બરાબર આ જ કરે છે (`librocksdb-dev` ઇન્સ્ટોલ કરો, પ્રોગ્રામ એડેપ્ટરો, ચલાવો
25M પંક્તિ મેટ્રિક્સ, આર્ટિફેક્ટ અપલોડ કરો અને જ્યારે `backfill=true`) પૃષ્ઠને સીધું જ બેકફિલ કરો.

### કેલિબર

- **ડેટા/કેશ રેશિયો**: 25,000,000 પંક્તિઓ × 116 B ≈ 2766 MiB ડેટા, 256 MiB કેશ પ્રતિ એન્જિન,
  ≈ 11:1, 97 GiB ડેટા/6 GiB કેશ (≈ 16:1) ની RocksDB ની સત્તાવાર સમીક્ષા સાથે સંરેખિત.
- **કેશની સમાન રકમ**: fkvનું પેજ કેશ (ઇન્ડેક્સ/ડેટા સમાન પૂલ), RocksDB ની બ્લોક કેશ
  (`cache_index_and_filter_blocks=true`, બ્લોક સાઇઝ 4 KiB), fjall ની પોતાની બ્લોક કેશ
  બજેટ તમામ બાઇટ્સ સમાન સંખ્યા પર સેટ છે.
- **પર્સિસ્ટન્સ કેલિબર (સરખામણી કૉલમ ગોઠવણી વિના, RocksDB ડિફોલ્ટ ગોઠવણીનો ઉપયોગ કરે છે)**: fkv 1×ડેટા પૃષ્ઠ + બેચ દીઠ
  1×મેનિફેસ્ટ `fdatasync` (Isomorphic to SyncData + AppendManifest of C++ EloqStore,
  બેમાંથી એક બંધ સ્વીચ નથી); RocksDB કૉલમ **ડિફૉલ્ટ રૂપરેખાંકન** નો ઉપયોગ કરે છે (WAL ચાલુ, `WriteOptions.sync=false`,
  કોઈ ક્રમિક fsync નથી), fjall પણ ડિફોલ્ટ (`PersistMode::Buffer`) નો ઉપયોગ કરે છે. તેથી લખવાનો તબક્કો (સિંગલ લખો /
  બેચ રાઇટ્સ) વચ્ચેનો તફાવત એ **દ્રઢતાની શક્તિનો તફાવત** છે, અમલીકરણ તફાવત નથી, જે નંબર સાથે પૃષ્ઠ પર જણાવવો આવશ્યક છે.
  જો તમે "સમાન સમન્વયન શક્તિ હેઠળ કોણ ઝડપી છે" તેનું વિશ્લેષણ કરવા માંગતા હો, તો `--align-fsync` ઉમેરો (Sync=true સાથે RocksDB ખોલો,
  fjall SyncAll નો ઉપયોગ કરે છે), આ વિકલ્પ બાહ્ય રીતે પ્રકાશિત મેટ્રિસિસ માટે ઉપયોગમાં લેવાતો નથી.
- **બે fkv ડ્રાઇવરો**: `--fkv-driver store` (ડિફૉલ્ટ, પ્રક્રિયામાં સીધા જ એક `Store` સાથે જોડાયેલ છે, અને
  RocksDB / fjall પણ લાઇબ્રેરી કૉલ્સ છે) અને `--fkv-driver runtime` (ડિપ્લોયમેન્ટ મોડ: એક પ્રક્રિયા
  `--fkv-shards` શાર્ડ થ્રેડો, વિનંતીઓ કી દ્વારા રૂટ કરવામાં આવે છે, C++ EloqStore ના સાર્વજનિક વાંચન અને લેખન સાથે સંરેખિત થાય છે
  ઇન્ટરફેસ). બાદમાંની દરેક વિનંતીને કતાર + ક્રોસ-થ્રેડ વેક-અપ, મૂળ (macOS, ફાઇલ IO થ્રેડ પૂલમાંથી પસાર થવાની જરૂર છે)
  વાંચનનો સમય લગભગ 20 µs/સમય છે, જે પ્રક્રિયામાં ડાયરેક્ટ કનેક્શન કરતાં ધીમો તીવ્રતાનો ક્રમ છે; Linux/io_uring પર ઘણું સસ્તું, પરંતુ
  હજુ એક જમ્પ. પેજ મેટ્રિક્સ સ્ટોર કેલિબરનો ઉપયોગ કરે છે, અને રનટાઇમ કેલિબરનો ઉપયોગ "ડિપ્લોયમેન્ટ ફોર્મ વિ C++ માટે થાય છે.
  "પબ્લિક ઇન્ટરફેસ" ની સરખામણી (fkv રનટાઇમ સિંગલ-થ્રેડ રીડિંગ લગભગ 50 kops/s છે, C++ EloqStore FFI સિંગલ-થ્રેડ
  લગભગ 21 કોપ્સ/સેકંડ).
- **કોન્કરન્સી કેલિબર વાંચો**: fkv સાઇડ થ્રેડ નંબર = `min(readers, --read-max-concurrency)`, ડિફોલ્ટ
  ઉપલી મર્યાદા 4 છે (મૂલ્યાંકન મશીન vCPU સાથે સંરેખિત), **નથી** "વાચક દીઠ એક થ્રેડ" - ઓળંગી ગયેલ સ્તર માત્ર કતારમાં વધારો કરે છે;
  થ્રેડ દીઠ કેશ = 256 MiB / થ્રેડોની સંખ્યા (કુલ રકમ નિશ્ચિત છે, વાચકો સાથે કાપલી નથી), અને વપરાયેલ
  `FuturesUnordered` ફ્લાય પર `--read-window` (ડિફૉલ્ટ 16) વિનંતીઓ રાખો. RocksDB બાજુ છે
  `readers` દરેક `std::thread` વારાફરતી વાંચે છે; fjall બાજુ પર સિંગલ-થ્રેડેડ લૂપ (વાચક ગિયરને અવગણીને,
  ફક્ત સંદર્ભ કૉલમ તરીકે). `--no-fkv-read-threads` "એક જ રનટાઇમ પર ઇન્ટરલીવ્ડ N અસિંક્રોનસ ચેઇન્સ" પર પાછા ડિજનરેટ થઈ શકે છે.
  તે પાઇપલાઇનની ઊંડાઈ છે, સંમતિ નથી, અને સમગ્ર એન્જિનમાં તુલનાત્મક નથી.
- **len()**: ત્રણમાંથી કોઈ પણ એન્જિનમાં O(1) કાઉન્ટિંગ ઈન્ટરફેસ નથી. આ લાઇન સંપૂર્ણ ટેબલ ગણના દર છે, O(1) લુકઅપ નથી.
