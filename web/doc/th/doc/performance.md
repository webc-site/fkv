# ประสิทธิภาพ

`fkv_bench` ทดสอบการเขียน อ่าน และสแกนโหลดบนพื้นที่คีย์คงที่

```bash
cargo run --release -p fkv_bench -- \
  --workload write-read --rows 20000 --batch-size 100
```

ตัวบ่งชี้ประกอบด้วยปริมาณงาน เวลาแฝงในแต่ละขั้นตอน และ RSS สูงสุด ปล่อยเวิร์กโฟลว์ปล่อย x86_64 /
`fkv_bench` ไบนารีสำหรับ aarch64

## การจับคู่สามทางกับ RocksDB/fjall

`crate/perf/fkv_compare` ใช้สเตจไดรเวอร์เดียวกันและการเข้ารหัสคีย์เดียวกัน (ตัวห้อย big-endian ขนาด 8 ไบต์ที่ส่วนท้าย
ลำดับพจนานุกรมสอดคล้องกับลำดับตัวห้อย) ทดสอบ fkv, RocksDB, fjall: RocksDB ผ่าน
`crate/perf/fkv_compare/cpp/rocksdb_ffi.cpp` ไลบรารีที่ใช้ร่วมกันที่คอมไพล์แล้วถูกโหลดด้วย dlopen (ไฟล์ C
ABI, Rust build ไม่ได้เชื่อมโยงกับ RocksDB), fjall ใช้ `fjall 3` โดยตรง เอ็นจิ้นทั้งสามแต่ละตัวจะเปิดไลบรารี
ก้าวหน้าในไลบรารีเดียวกันตามลำดับขั้นตอน: การโหลดจำนวนมากจะสร้างข้อมูล จากนั้น len / การอ่านจุด / การอ่านช่วง /
การลบทั้งหมดจะส่งผลต่อข้อมูลเดียวกัน

```bash
cargo build --release -p fkv_compare
bash scripts/perf/build_rocksdb_ffi.sh # ข้ามคอลัมน์ที่สามหากไม่มี RocksDB
./target/release/fkv_compare \
  --rows 25000000 --bulk-rows 25000000 --cache-bytes 268435456 \
  --readers 1,4,8,16,32 --workdir /tmp/fkv-compare \
  --rocksdb-lib target/perf/librocksdb_bench_ffi.so \
  --json /tmp/fkv-compare.json
```

ตัวเลขสำหรับเมทริกซ์หน้าแรกสามารถมาจากการดำเนินการที่ติดตามได้เพียงครั้งเดียวเท่านั้น:

```bash
python3 scripts/perf/fkv_compare_to_js.py \
  --json /tmp/fkv-compare.json --perf-js web/src/conf/perf.js \
  --machine "..." --source "เรียกใช้ CI <id>"
```

GitHub Actions' `perf.yml` ทำสิ่งนี้ทุกประการ (ติดตั้ง `librocksdb-dev`, อะแดปเตอร์โปรแกรม, รัน
เมทริกซ์แถว 25M อัปโหลดส่วนประดิษฐ์ และทดแทนหน้าเว็บโดยตรงเมื่อ `backfill=true`)

### ความสามารถ

- **อัตราส่วนข้อมูล/แคช**: 25,000,000 แถว × 116 B กลับไปยังข้อมูล 2766 MiB, แคช 256 MiB ต่อเครื่องยนต์
  µ 11: 1 ซึ่งสอดคล้องกับการตรวจสอบอย่างเป็นทางการของ RocksDB เกี่ยวกับข้อมูล 97 GiB / แคช 6 GiB ( 16: 1 )
- **จำนวนแคชเท่ากัน**: แคชเพจของ fkv (ดัชนี/ข้อมูลพูลเดียวกัน), แคชบล็อกของ RocksDB
  (`cache_index_and_filter_blocks=true`, ขนาดบล็อก 4 KiB), บล็อกแคชของ fjall เอง
  งบประมาณทั้งหมดถูกตั้งค่าเป็นจำนวนไบต์เท่ากัน
- **ความสามารถคงอยู่ (คอลัมน์เปรียบเทียบใช้การกำหนดค่าเริ่มต้นของ RocksDB โดยไม่มีการจัดตำแหน่ง)**: fkv 1×หน้าข้อมูล + ต่อชุด
  1×manifest `fdatasync` (Isomorphic เป็น SyncData + ผนวก Manifest ของ C++ EloqStore,
  ไม่มีสวิตช์ปิด) คอลัมน์ RocksDB ใช้ **การกำหนดค่าเริ่มต้น** (เปิด WAL, `WriteOptions.sync=false`,
  ไม่มี fsync ตามลำดับ) fjall ยังใช้ค่าเริ่มต้น (`PersistMode::Buffer`) ดังนั้นขั้นตอนการเขียน (single write /
  ความแตกต่างระหว่างการเขียนเป็นชุด) คือ **ความแตกต่างด้านความคงอยู่** ไม่ใช่ความแตกต่างในการใช้งาน ซึ่งจะต้องระบุไว้บนหน้าพร้อมกับตัวเลข
  หากคุณต้องการวิเคราะห์ "ใครเร็วกว่าภายใต้ความแรงของการซิงโครไนซ์เดียวกัน" ให้เพิ่ม `--align-fsync` (เปิด RocksDB ด้วย sync=true,
  fjall ใช้ SyncAll) ตัวเลือกนี้ไม่ได้ใช้สำหรับเมทริกซ์ที่เผยแพร่ภายนอก
- **ไดรเวอร์ fkv สองตัว**: `--fkv-driver store` (ค่าเริ่มต้น เชื่อมต่อโดยตรงกับ `Store` ตัวเดียวภายในกระบวนการ และ
  RocksDB / fjall เป็นการเรียกไลบรารีด้วย) และ `--fkv-driver runtime` (โหมดการปรับใช้: กระบวนการ
  `--fkv-shards` เธรดย่อย คำขอถูกกำหนดเส้นทางด้วยคีย์ ซึ่งสอดคล้องกับการอ่านและการเขียนสาธารณะของ C++ EloqStore
  อินเตอร์เฟซ) แต่ละคำขออย่างหลังจะต้องผ่านคิว + การปลุกแบบข้ามเธรด, เนทิฟ (macOS, ไฟล์ IO ผ่านพูลเธรด)
  เวลาในการอ่านคือประมาณ 20 µs/ครั้ง ซึ่งเป็นลำดับความสำคัญช้ากว่าการเชื่อมต่อโดยตรงในกระบวนการ ราคาถูกกว่ามากบน Linux/io_uring แต่
  ยังโดดอยู่เลย เมทริกซ์หน้าใช้ความสามารถร้านค้าและความสามารถรันไทม์ใช้สำหรับ "แบบฟอร์มการปรับใช้เทียบกับ C ++
  การเปรียบเทียบ "อินเทอร์เฟซสาธารณะ" (การอ่านเธรดเดี่ยวรันไทม์ fkv อยู่ที่ประมาณ 50 kops/s, C++ EloqStore FFI เธรดเดี่ยว
  ส่วนแบ่งประมาณ 21 kops/s)
- **อ่านความสามารถการทำงานพร้อมกัน**: หมายเลขเธรดด้าน fkv = `min(readers, --read-max-concurrency)` ค่าเริ่มต้น
  ขีดจำกัดบนคือ 4 (สอดคล้องกับ vCPU ของเครื่องประเมินผล) **ไม่ใช่** "หนึ่งเธรดต่อผู้อ่าน" - ระดับที่เกินจะเพิ่มคิวเท่านั้น
  แคชต่อเธรด = 256 MiB / จำนวนเธรด (จำนวนรวมได้รับการแก้ไขแล้ว ไม่ทำลายด้วยตัวอ่าน) และใช้
  `FuturesUnordered` เก็บคำขอ `--read-window` (ค่าเริ่มต้น 16) ไว้ได้ทันที ด้าน RocksDB คือ
  `readers` แต่ละ `std::thread` อ่านพร้อมกัน วนซ้ำแบบเธรดเดียวที่ด้าน fjall (โดยไม่สนใจเกียร์ของผู้อ่าน
  เป็นคอลัมน์อ้างอิงเท่านั้น) `--no-fkv-read-threads` สามารถลดระดับกลับไปเป็น "ลูกโซ่อะซิงโครนัส N แบบอินเทอร์ลีฟบนรันไทม์เดียว"
  นั่นคือความลึกของไปป์ไลน์ ไม่ใช่การทำงานพร้อมกัน และไม่สามารถเทียบเคียงได้กับเครื่องยนต์ต่างๆ
- **len()**: ไม่มีเอ็นจิ้นทั้งสามตัวที่มีอินเทอร์เฟซการนับ O(1) บรรทัดนี้เป็นอัตราการนับตารางทั้งหมด ไม่ใช่การค้นหา O(1)
