# أداء

`fkv_bench` اختبار عمليات الكتابة والقراءة والمسح الضوئي على مساحة مفتاح ثابتة.

```bash
cargo run --release -p fkv_bench -- \
  --workload write-read --rows 20000 --batch-size 100
```

تشمل المؤشرات الإنتاجية وزمن الوصول في كل مرحلة وذروة RSS. إصدار سير العمل x86_64 /
`fkv_bench` ثنائي لـ aarch64.

## تطابق ثلاثي مع RocksDB/fjall

`crate/perf/fkv_compare` استخدم نفس برنامج تشغيل المرحلة ونفس تشفير المفتاح (خط منخفض كبير 8 بايت في النهاية،
ترتيب القاموس يتوافق مع الترتيب المنخفض) اختبار fkv، RocksDB، fjall: تم اجتياز RocksDB
`crate/perf/fkv_compare/cpp/rocksdb_ffi.cpp` يتم تحميل المكتبة المشتركة المترجمة باستخدام dlopen (نفس C
ABI، لا يرتبط بناء Rust بـ RocksDB)، يستخدم fjall `fjall 3` مباشرة. يفتح كل محرك من المحركات الثلاثة مكتبة.
التقدم على نفس المكتبة بترتيب المراحل: التحميل المجمع ينشئ البيانات، ثم لين / قراءة النقطة / قراءة النطاق /
تؤثر جميع عمليات الحذف على نفس البيانات.

```bash
cargo build --release -p fkv_compare
bash scripts/perf/build_rocksdb_ffi.sh # تخطي العمود الثالث في حالة عدم وجود RocksDB
./target/release/fkv_compare \
  --rows 25000000 --bulk-rows 25000000 --cache-bytes 268435456 \
  --readers 1,4,8,16,32 --workdir /tmp/fkv-compare \
  --rocksdb-lib target/perf/librocksdb_bench_ffi.so \
  --json /tmp/fkv-compare.json
```

لا يمكن أن تأتي أرقام مصفوفة الصفحة الرئيسية إلا من عملية تشغيل واحدة يمكن تتبعها:

```bash
python3 scripts/perf/fkv_compare_to_js.py \
  --json /tmp/fkv-compare.json --perf-js web/src/conf/perf.js \
  --machine "..." --source "تشغيل CI <id>"
```

يقوم `perf.yml` الخاص بـ GitHub Actions بهذا بالضبط (تثبيت `librocksdb-dev`، محولات البرنامج، تشغيل
مصفوفة صف 25M، وتحميل قطعة أثرية، وملء الصفحة مباشرة عندما `backfill=true`).

### عيار

- **نسبة البيانات/ذاكرة التخزين المؤقت**: 25,000,000 صف × 116 بايت ≈ 2766 ميجا بايت من البيانات، 256 ميجا بايت من ذاكرة التخزين المؤقت لكل محرك،
  ≈ 11:1، متوافق مع المراجعة الرسمية لـ RocksDB لـ 97 بيانات GiB/6 GiB ذاكرة تخزين مؤقت (≈ 16:1).
- ** نفس مقدار ذاكرة التخزين المؤقت **: ذاكرة التخزين المؤقت لصفحة fkv (مجموعة الفهرس/البيانات نفسها)، وذاكرة التخزين المؤقت لكتلة RocksDB
  (`cache_index_and_filter_blocks=true`، حجم الكتلة 4 كيلو بايت)، ذاكرة التخزين المؤقت للكتلة الخاصة بـ fjall
  يتم تعيين كافة الميزانيات على نفس العدد من البايتات.
- ** عيار الثبات (يستخدم عمود المقارنة التكوين الافتراضي RocksDB، بدون محاذاة) **: fkv 1 × صفحة بيانات + لكل دفعة
  1×البيان `fdatasync` (متماثل إلى SyncData + AppendManifest of C++ EloqStore،
  لا يحتوي أي منهما على مفتاح إيقاف)؛ يستخدم عمود RocksDB **التكوين الافتراضي** (WAL on، `WriteOptions.sync=false`،
  لا يوجد fsync متسلسل)، يستخدم fjall أيضًا الإعداد الافتراضي (`PersistMode::Buffer`). وبالتالي فإن مرحلة الكتابة (الكتابة المفردة /
  الفرق بين عمليات الكتابة المجمعة) هو **فرق قوة الثبات**، وليس فرق التنفيذ، الذي يجب ذكره في الصفحة مع الرقم.
  إذا كنت تريد تحليل "من هو الأسرع بنفس قوة المزامنة"، أضف `--align-fsync` (افتح RocksDB باستخدام sync=true،
  يستخدم fjall SyncAll)، ولا يتم استخدام هذا الخيار للمصفوفات المنشورة خارجيًا.
- **اثنين من برامج تشغيل fkv**: `--fkv-driver store` (افتراضي، متصل مباشرة بـ `Store` واحد داخل العملية، و
  RocksDB / fjall هي أيضًا استدعاءات للمكتبة) و`--fkv-driver runtime` (وضع النشر: عملية
  `--fkv-shards` سلاسل الأجزاء، يتم توجيه الطلبات عن طريق المفتاح، بما يتماشى مع القراءة والكتابة العامة لـ C++ EloqStore
  واجهة). يحتاج كل طلب من الأخير إلى المرور عبر قائمة الانتظار + تنبيه عبر سلسلة المحادثات، أصلي (macOS، يمر إدخال الملف عبر تجمع مؤشرات الترابط)
  يبلغ وقت القراءة حوالي 20 ميكروثانية/الوقت، وهو أمر أبطأ من حيث الحجم من الاتصال المباشر أثناء العملية؛ أرخص بكثير على Linux/io_uring، ولكن
  لا تزال قفزة. تستخدم مصفوفة الصفحة عيار المتجر، ويتم استخدام عيار وقت التشغيل لـ "نموذج النشر مقابل C++".
  مقارنة "الواجهة العامة" (قراءة الخيط المفرد في وقت تشغيل fkv تبلغ حوالي 50 كوب/ثانية، ومؤشر الترابط المفرد C++ EloqStore FFI
  شظية حوالي 21 كوب/ثانية).
- ** قراءة عيار التزامن **: رقم مؤشر الترابط الجانبي fkv = `min(readers, --read-max-concurrency)`، افتراضي
  الحد الأعلى هو 4 (متوافق مع وحدة المعالجة المركزية الافتراضية لجهاز التقييم)، **وليس** "موضوع واحد لكل قارئ" - المستوى الذي تم تجاوزه يزيد فقط من قائمة الانتظار؛
  ذاكرة التخزين المؤقت لكل موضوع = 256 ميجابايت / عدد المواضيع (الكمية الإجمالية ثابتة، غير ممزقة مع القراء)، وتستخدم
  `FuturesUnordered` احتفظ بالطلبات `--read-window` (الافتراضي 16) أثناء التنقل. الجانب RocksDB هو
  `readers` يقرأ كل `std::thread` في وقت واحد؛ حلقة ذات خيط واحد على الجانب fjall (تجاهل معدات القراء،
  كعمود مرجعي فقط). `--no-fkv-read-threads` يمكن أن يتدهور مرة أخرى إلى "سلاسل N غير المتزامنة المتداخلة في وقت تشغيل واحد".
  هذا هو عمق خط الأنابيب، وليس التزامن، ولا يمكن مقارنته عبر المحركات.
- **len()**: لا يحتوي أي من المحركات الثلاثة على واجهات عد O(1). هذا الخط هو معدل العد الكامل للجدول، وليس بحث O(1).
