# წარმადობა

`fkv_bench` ჩაწერის, წაკითხვისა და სკანირების ტესტირება გასაღების ფიქსირებულ სივრცეზე.

```bash
cargo run --release -p fkv_bench -- \
  --workload write-read --rows 20000 --batch-size 100
```

ინდიკატორები მოიცავს გამტარუნარიანობას, შეყოვნებას თითოეულ ეტაპზე და პიკს RSS. სამუშაო ნაკადის გამოშვება x86_64 /
`fkv_bench` ბინარული aarch64-ისთვის.

## სამმხრივი შეხამება RocksDB/fjall-თან

`crate/perf/fkv_compare` გამოიყენეთ იგივე ეტაპის დრაივერი და იგივე კლავიშის კოდირება (8-ბაიტი დიდი-ენდიანის ხელმოწერა ბოლოს,
ლექსიკონის თანმიმდევრობა შეესაბამება ხელმოწერის მიმდევრობას) ტესტი fkv, RocksDB, fjall: RocksDB გაიარა
`crate/perf/fkv_compare/cpp/rocksdb_ffi.cpp` შედგენილი საზიარო ბიბლიოთეკა იტვირთება dlopen-ით (იგივე C
ABI, Rust build არ უკავშირდება RocksDB-ს), fjall პირდაპირ იყენებს `fjall 3`-ს. სამი ძრავიდან თითოეული ხსნის ბიბლიოთეკას.
გადადით იმავე ბიბლიოთეკაზე ეტაპების თანმიმდევრობით: ნაყარი დატვირთვა ქმნის მონაცემებს და შემდეგ len / წერტილის კითხვა / დიაპაზონის კითხვა /
წაშლა ყველა გავლენას ახდენს ერთსა და იმავე მონაცემებზე.

```bash
cargo build --release -p fkv_compare
bash scripts/perf/build_rocksdb_ffi.sh # გამოტოვეთ მესამე სვეტი, თუ არ არის RocksDB
./target/release/fkv_compare \
  --rows 25000000 --bulk-rows 25000000 --cache-bytes 268435456 \
  --readers 1,4,8,16,32 --workdir /tmp/fkv-compare \
  --rocksdb-lib target/perf/librocksdb_bench_ffi.so \
  --json /tmp/fkv-compare.json
```

საწყისი გვერდის მატრიცის ნომრები შეიძლება იყოს მხოლოდ ერთი მიკვლევადი გაშვებიდან:

```bash
python3 scripts/perf/fkv_compare_to_js.py \
  --json /tmp/fkv-compare.json --perf-js web/src/conf/perf.js \
  --machine "..." --source "CI run <id>"
```

GitHub Actions-ის `perf.yml` აკეთებს ზუსტად ამას (დააინსტალირეთ `librocksdb-dev`, პროგრამის გადამყვანები, გაუშვით
25M მწკრივის მატრიცა, ატვირთეთ არტეფაქტი და პირდაპირ შეავსეთ გვერდი, როდესაც `backfill=true`).

### კალიბრის

- **მონაცემთა/ქეშის თანაფარდობა**: 25,000,000 მწკრივი × 116 B ≈ 2766 MiB მონაცემები, 256 MiB ქეში თითო ძრავზე,
  ≈ 11:1, შეესაბამება RocksDB-ის ოფიციალურ მიმოხილვას 97 გიბ მონაცემები/6 გიბაიტი ქეში (≈ 16:1).
- ** ქეშის იგივე რაოდენობა **: fkv-ის გვერდის ქეში (ინდექსი/მონაცემების იგივე ფონდი), RocksDB-ის ბლოკის ქეში
  (`cache_index_and_filter_blocks=true`, ბლოკის ზომა 4 KiB), fjall-ის საკუთარი ბლოკის ქეში
  ყველა ბიუჯეტი დაყენებულია ბაიტების იმავე რაოდენობაზე.
- ** მდგრადობის კალიბრი (შედარების სვეტი იყენებს RocksDB ნაგულისხმევ კონფიგურაციას, გასწორების გარეშე)**: fkv 1×მონაცემთა გვერდი + თითო პარტიაში
  1×მანიფესტი `fdatasync` (იზომორფული SyncData + AppendManifest of C++ EloqStore,
  არც გამომრთველი აქვს); RocksDB სვეტი იყენებს **ნაგულისხმევ კონფიგურაციას** (WAL ჩართულია, `WriteOptions.sync=false`,
  თანმიმდევრული fsync არ არის), fjall ასევე იყენებს ნაგულისხმევს (`PersistMode::Buffer`). ამიტომ ჩაწერის ფაზა (ერთჯერადი ჩაწერა /
  განსხვავება ჯგუფურ ჩაწერას შორის) არის **მდგრადობის სიძლიერის განსხვავება** და არა განხორციელების განსხვავება, რომელიც უნდა იყოს მითითებული გვერდზე რიცხვთან ერთად.
  თუ გსურთ გააანალიზოთ „ვინ არის უფრო სწრაფი სინქრონიზაციის იგივე სიძლიერის პირობებში“, დაამატეთ `--align-fsync` (გახსენით RocksDB sync=true,
  fjall იყენებს SyncAll), ეს პარამეტრი არ გამოიყენება გარედან გამოქვეყნებული მატრიცებისთვის.
- **ორი fkv დრაივერი**: `--fkv-driver store` (ნაგულისხმევი, უშუალოდ დაკავშირებულია ერთ `Store` პროცესში, და
  RocksDB / fjall ასევე არის ბიბლიოთეკის ზარები) და `--fkv-driver runtime` (განლაგების რეჟიმი: პროცესი
  `--fkv-shards` ფრაგმენტული ძაფები, მოთხოვნების მარშრუტირება ხდება გასაღებით, შეესაბამება C++ EloqStore-ის საჯარო კითხვასა და წერას
  ინტერფეისი). ამ უკანასკნელის თითოეულმა მოთხოვნამ უნდა გაიაროს რიგი + ძაფების გაღვიძება, მშობლიური (macOS, ფაილი IO გადის ძაფების აუზში)
  წაკითხვის დრო არის დაახლოებით 20 μs/დრო, რაც სიდიდის რიგითობით უფრო ნელია, ვიდრე უშუალოდ პროცესის დროს; ბევრად იაფია Linux/io_uring-ზე, მაგრამ
  ჯერ კიდევ ნახტომი. გვერდის მატრიცა იყენებს მაღაზიის კალიბრს, ხოლო გაშვების კალიბრი გამოიყენება "განლაგების ფორმის წინააღმდეგ C++
  "საჯარო ინტერფეისის" შედარება (fkv გაშვების ერთ ძაფზე წაკითხვა არის დაახლოებით 50 კოპ/წმ, C++ EloqStore FFI ერთი ძაფი
  ნატეხი დაახლოებით 21 კოპი/წმ).
- ** წაკითხული კონკურენტულობის კალიბრი **: fkv გვერდითი ძაფის ნომერი = `min(readers, --read-max-concurrency)`, ნაგულისხმევი
  ზედა ზღვარი არის 4 (შეესაბამება vCPU შეფასების მანქანას), **არა** „ერთი თემა თითო მკითხველზე“ - გადაჭარბებული დონე მხოლოდ ზრდის რიგს;
  ქეში თითო ძაფზე = 256 მიბაიტი / ძაფების რაოდენობა (მთლიანი თანხა ფიქსირდება, არ იშლება მკითხველებთან) და გამოიყენება
  `FuturesUnordered` შეინახეთ `--read-window` (ნაგულისხმევი 16) მოთხოვნები. RocksDB მხარე არის
  `readers` თითოეული `std::thread` იკითხება ერთდროულად; ერთი ძაფის მარყუჟი fjall-ის მხარეს (მკითხველის მექანიზმის იგნორირება,
  მხოლოდ საცნობარო სვეტად). `--no-fkv-read-threads` შეიძლება გადაგვარდეს "გადაკვეთილ N ასინქრონულ ჯაჭვებამდე ერთი გაშვების დროს".
  ეს არის მილსადენის სიღრმე, არა კონკურენტულობა და არ არის შედარებადი ძრავებში.
- **len()**: სამი ძრავიდან არცერთს არ აქვს O(1) დათვლის ინტერფეისი. ეს ხაზი არის ცხრილის სრული დათვლის მაჩვენებელი და არა O(1) ძიება.
