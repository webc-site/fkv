# Перформанси

`fkv_bench` Тестирајте ги оптоварувањата за пишување, читање и скенирање на фиксен простор за клучеви.

```bash
cargo run --release -p fkv_bench -- \
  --workload write-read --rows 20000 --batch-size 100
```

Индикаторите вклучуваат пропусност, латентност во секоја фаза и врвен RSS. ослободување на работниот тек ослободување x86_64 /
`fkv_bench` бинарен за aarch64.

## Тројно спојување со RocksDB/fjall

`crate/perf/fkv_compare` Користете го истиот двигател на сцената и истото кодирање на копчињата (8-бајти биг-ендијански претплата на крајот,
Редоследот на речник е конзистентен со редоследот на претплатата) Тест fkv, RocksDB, fjall: RocksDB помина
`crate/perf/fkv_compare/cpp/rocksdb_ffi.cpp` Компилираната споделена библиотека е вчитана со dlopen (истиот C
ABI, Rust build не се поврзува со RocksDB), fjall директно користи `fjall 3`. Секој од трите мотори отвора библиотека.
Напредувајте во истата библиотека по редослед на фази: масовното оптоварување создава податоци, а потоа len / читање точка / читање опсег /
Сите бришења влијаат на истите податоци.

```bash
cargo build --release -p fkv_compare
bash скрипти/perf/build_rocksdb_ffi.sh # Прескокнете ја третата колона ако нема RocksDB
./target/release/fkv_compare \
  --rows 25000000 --bulk-rows 25000000 --cache-bytes 268435456 \
  --readers 1,4,8,16,32 --workdir /tmp/fkv-compare \
  --rocksdb-lib target/perf/librocksdb_bench_ffi.so \
  --json /tmp/fkv-compare.json
```

Броевите за матрицата на почетната страница можат да дојдат само од едно следење:

```bash
python3 scripts/perf/fkv_compare_to_js.py \
  --json /tmp/fkv-compare.json --perf-js web/src/conf/perf.js \
  --machine "..." --извор "CI run <id>"
```

GitHub Actions' `perf.yml` го прави токму тоа (инсталирајте `librocksdb-dev`, програмски адаптери, стартувајте
Матрица на редови од 25 милиони, прикачете артефакт и директно пополнете ја страницата кога `backfill=true`).

### калибар

- **Сооднос на податоци/кеш**: 25.000.000 редови × 116 B ≈ 2766 MiB податоци, 256 MiB кеш по мотор,
  ≈ 11:1, усогласен со официјалниот преглед на RocksDB за 97 GiB податоци/6 GiB кеш (≈ 16:1).
- **Иста количина кеш**: кеш на страницата на fkv (ист базен индекс/податоци), блок кеш на RocksDB
  (`cache_index_and_filter_blocks=true`, големина на блок 4 KiB), сопствен блок кеш на fjall
  Сите буџети се поставени на ист број бајти.
- **Калибар на упорност (колоната за споредба ја користи стандардната конфигурација на RocksDB, без порамнување)**: fkv 1×страница со податоци + по серија
  1×манифест `fdatasync` (изоморфен на SyncData + AppendManifest на C++ EloqStore,
  Ниту еден нема прекинувач за исклучување); колоната RocksDB ја користи **стандардната конфигурација** (WAL вклучен, `WriteOptions.sync=false`,
  Без секвенцијално fsync), fjall исто така го користи стандардното (`PersistMode::Buffer`). Затоа фазата на пишување (едно пишување /
  Разликата помеѓу записите во серија) е **разликата на јачината на упорноста**, а не разликата во имплементацијата, која мора да биде наведена на страницата заедно со бројот.
  Ако сакате да анализирате „кој е побрз со иста сила на синхронизација“, додајте `--align-fsync` (отворете RocksDB со sync=true,
  fjall користи SyncAll), оваа опција не се користи за надворешно објавени матрици.
- **Два fkv драјвери**: `--fkv-driver store` (стандардно, директно поврзан со еден `Store` во процесот, и
  RocksDB / fjall се исто така библиотечни повици) и `--fkv-driver runtime` (режим на распоредување: процес
  `--fkv-shards` парчиња нишки, барањата се пренасочуваат со клуч, усогласени со јавното читање и пишување на C++ EloqStore
  интерфејс). Секое барање на второто треба да помине низ редот + будење со вкрстени нишки, мајчин (macOS, IO датотеката поминува низ базенот на нишки)
  Времето на читање е околу 20 µs/време, што е ред на големина побавно од директната врска во процесот; многу поевтино на Linux/io_uring, но
  Сепак скок. Матрицата на страницата го користи калибарот на продавницата, а калибарот на траење се користи за „форма за распоредување наспроти C++
  Споредба на „Јавен интерфејс“ (читањето на една нишка на траење на fkv е околу 50 kops/s, C++ EloqStore FFI со една нишка
  фрагмент околу 21 коп/с).
- **Калибар на истовремена читање**: број на странична нишка fkv = `min(readers, --read-max-concurrency)`, стандардно
  Горната граница е 4 (усогласена со vCPU машината за оценување), **не** „една нишка по читач“ - надминатото ниво само ја зголемува редицата;
  Кеш по нишка = 256 MiB / број на нишки (вкупниот износ е фиксен, не се распарчува со читачи) и се користи
  `FuturesUnordered` Чувајте ги барањата `--read-window` (стандардно 16) во лет. RocksDB страна е
  `readers` Секој `std::thread` чита истовремено; јамка со една нишка на страната fjall (игнорирање на опремата на читателите,
  Само како референтна колона). `--no-fkv-read-threads` може да се дегенерира назад во „преплетени N асинхрони синџири на едно време на траење“.
  Тоа е длабочина на цевководот, а не истовременост и не може да се спореди со моторите.
- **len()**: Ниту еден од трите мотори нема интерфејси за броење O(1). Оваа линија е стапка на броење на целосната табела, а не пребарување на O(1).
