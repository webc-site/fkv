# পারফরম্যান্স

`fkv_bench` একটি নির্দিষ্ট কী স্পেসে লোড লিখুন, পড়ুন এবং স্ক্যান করুন।

```bash
cargo run --release -p fkv_bench -- \
  --workload write-read --rows 20000 --batch-size 100
```

সূচকগুলির মধ্যে রয়েছে থ্রুপুট, প্রতিটি পর্যায়ে লেটেন্সি এবং সর্বোচ্চ RSS। রিলিজ ওয়ার্কফ্লো রিলিজ x86_64 /
aarch64 এর জন্য `fkv_bench` বাইনারি।

## RocksDB/fjall-এর সাথে থ্রি-ওয়ে ম্যাচআপ

`crate/perf/fkv_compare` একই স্টেজ ড্রাইভার এবং একই কী এনকোডিং ব্যবহার করুন (শেষে 8-বাইট বড়-এন্ডিয়ান সাবস্ক্রিপ্ট,
অভিধানের ক্রম সাবস্ক্রিপ্ট অর্ডারের সাথে সামঞ্জস্যপূর্ণ) পরীক্ষা fkv, RocksDB, fjall: RocksDB পাস
`crate/perf/fkv_compare/cpp/rocksdb_ffi.cpp` সংকলিত শেয়ার্ড লাইব্রেরিটি dlopen (একই C) দিয়ে লোড করা হয়েছে
ABI, Rust বিল্ড RocksDB এর সাথে লিঙ্ক করে না), fjall সরাসরি `fjall 3` ব্যবহার করে। তিনটি ইঞ্জিনের প্রতিটি একটি লাইব্রেরি খোলে।
পর্যায়ক্রমে একই লাইব্রেরিতে অগ্রসর হওয়া: বাল্ক লোড ডেটা তৈরি করে এবং তারপরে লেন/পয়েন্ট রিডিং/রেঞ্জ রিডিং/
সমস্ত মুছে ফেলা একই ডেটা প্রভাবিত করে।

```bash
cargo build --release -p fkv_compare
bash scripts/perf/build_rocksdb_ffi.sh # রকসডিবি না থাকলে তৃতীয় কলামটি এড়িয়ে যান
./target/release/fkv_compare \
  --rows 25000000 --bulk-rows 25000000 --cache-bytes 268435456 \
  --readers 1,4,8,16,32 --workdir /tmp/fkv-compare \
  --rocksdb-lib target/perf/librocksdb_bench_ffi.so \
  --json /tmp/fkv-compare.json
```

হোমপেজ ম্যাট্রিক্সের সংখ্যা শুধুমাত্র একটি ট্রেসেবল রান থেকে আসতে পারে:

```bash
python3 scripts/perf/fkv_compare_to_js.py \
  --json /tmp/fkv-compare.json --perf-js web/src/conf/perf.js \
  --মেশিন "..." -- উৎস "CI রান <id>"
```

গিটহাব অ্যাকশনস' `perf.yml` ঠিক এই কাজটি করে (`librocksdb-dev` ইনস্টল করুন, প্রোগ্রাম অ্যাডাপ্টার, চালান
25M সারি ম্যাট্রিক্স, আর্টিফ্যাক্ট আপলোড করুন এবং `backfill=true` হলে সরাসরি পৃষ্ঠাটি ব্যাকফিল করুন।

### ক্যালিবার

- **ডেটা/ক্যাশ অনুপাত**: 25,000,000 সারি × 116 B ≈ 2766 MiB ডেটা, 256 MiB ক্যাশ প্রতি ইঞ্জিন,
  ≈ 11:1, 97 GiB ডেটা/6 GiB ক্যাশে (≈ 16:1) এর RocksDB-এর অফিসিয়াল পর্যালোচনার সাথে সারিবদ্ধ।
- **একই পরিমাণ ক্যাশে**: fkv-এর পৃষ্ঠা ক্যাশে (সূচি/ডেটা একই পুল), RocksDB-এর ব্লক ক্যাশে
  (`cache_index_and_filter_blocks=true`, ব্লক সাইজ 4 KiB), fjall এর নিজস্ব ব্লক ক্যাশে
  বাজেট সব একই সংখ্যা বাইট সেট করা হয়.
- **পার্সিস্টেন্স ক্যালিবার (তুলনা কলামটি সারিবদ্ধকরণ ছাড়াই RocksDB ডিফল্ট কনফিগারেশন ব্যবহার করে)**: fkv 1×ডেটা পৃষ্ঠা + প্রতি ব্যাচ
  1×manifest `fdatasync` (Isomorphic to SyncData + AppendManifest-এর C++ EloqStore,
  একটি বন্ধ সুইচ নেই); RocksDB কলাম **ডিফল্ট কনফিগারেশন** ব্যবহার করে (WAL চালু, `WriteOptions.sync=false`,
  কোন অনুক্রমিক fsync নেই, fjall এছাড়াও ডিফল্ট (`PersistMode::Buffer`) ব্যবহার করে। তাই লেখার পর্যায় (একক লিখুন /
  ব্যাচ লেখার মধ্যে পার্থক্য) হল **অধ্যবসায়ের শক্তির পার্থক্য**, বাস্তবায়নের পার্থক্য নয়, যা অবশ্যই সংখ্যার সাথে পৃষ্ঠায় উল্লেখ করতে হবে।
  আপনি যদি বিশ্লেষণ করতে চান "কে একই সিঙ্ক্রোনাইজেশন শক্তির অধীনে দ্রুত", যোগ করুন `--align-fsync` (sync=true সহ RocksDB খুলুন,
  fjall SyncAll ব্যবহার করে), এই বিকল্পটি বাহ্যিকভাবে প্রকাশিত ম্যাট্রিক্সের জন্য ব্যবহার করা হয় না।
- **দুটি fkv ড্রাইভার**: `--fkv-driver store` (ডিফল্ট, প্রক্রিয়ার মধ্যে একটি একক `Store` সাথে সরাসরি সংযুক্ত, এবং
  RocksDB / fjall এছাড়াও লাইব্রেরি কল) এবং `--fkv-driver runtime` (ডিপ্লয়মেন্ট মোড: একটি প্রক্রিয়া
  `--fkv-shards` শার্ড থ্রেড, অনুরোধগুলি কী দ্বারা রুট করা হয়, C++ EloqStore-এর সর্বজনীন পড়া এবং লেখার সাথে সারিবদ্ধ
  ইন্টারফেস)। পরেরটির প্রতিটি অনুরোধকে সারির মধ্য দিয়ে যেতে হবে + ক্রস-থ্রেড ওয়েক-আপ, নেটিভ (macOS, ফাইল IO থ্রেড পুলের মধ্য দিয়ে যায়)
  পড়ার সময় প্রায় 20 µs/টাইম, যা প্রক্রিয়াধীন সরাসরি সংযোগের চেয়ে ধীর গতির একটি ক্রম; Linux/io_uring-এ অনেক সস্তা, কিন্তু
  এখনও একটি লাফ. পৃষ্ঠা ম্যাট্রিক্স স্টোর ক্যালিবার ব্যবহার করে, এবং রানটাইম ক্যালিবার "ডিপ্লয়মেন্ট ফর্ম বনাম C++ এর জন্য ব্যবহৃত হয়
  "পাবলিক ইন্টারফেস" এর তুলনা (fkv রানটাইম একক-থ্রেড রিডিং প্রায় 50 kops/s, C++ EloqStore FFI একক-থ্রেড
  প্রায় 21 কোপ/সেকেন্ড)।
- **কনকারেন্সি ক্যালিবার পড়ুন**: fkv সাইড থ্রেড নম্বর = `min(readers, --read-max-concurrency)`, ডিফল্ট
  ঊর্ধ্ব সীমা হল 4 (মূল্যায়ন মেশিন vCPU-এর সাথে সারিবদ্ধ), **না** "একটি থ্রেড প্রতি পাঠক" - অতিক্রম করা মাত্রা শুধুমাত্র সারি বাড়ায়;
  প্রতি থ্রেড ক্যাশে = 256 MiB / থ্রেডের সংখ্যা (মোট পরিমাণ নির্দিষ্ট, পাঠকদের সাথে টুকরো টুকরো করা হয় না), এবং ব্যবহৃত
  `FuturesUnordered` ফ্লাইতে `--read-window` (ডিফল্ট 16) অনুরোধগুলি রাখুন৷ রকসডিবি পক্ষ হল
  `readers` প্রতিটি `std::thread` একই সাথে পড়ে; fjall পাশে একক-থ্রেডেড লুপ (পাঠক গিয়ার উপেক্ষা করে,
  শুধুমাত্র একটি রেফারেন্স কলাম হিসাবে)। `--no-fkv-read-threads` "একক রানটাইমে ইন্টারলিভড N অ্যাসিঙ্ক্রোনাস চেইন"-এ ফিরে যেতে পারে।
  এটি পাইপলাইনের গভীরতা, একযোগে নয় এবং ইঞ্জিন জুড়ে তুলনাযোগ্য নয়।
- **লেন()**: তিনটি ইঞ্জিনের কোনোটিতেই O(1) কাউন্টিং ইন্টারফেস নেই। এই লাইনটি সম্পূর্ণ টেবিল গণনা হার, O(1) লুকআপ নয়।
