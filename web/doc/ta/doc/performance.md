# செயல்திறன்

`fkv_bench` ஒரு நிலையான விசை இடத்தில் சுமைகளை எழுதவும், படிக்கவும் மற்றும் ஸ்கேன் செய்யவும்.

```bash
cargo run --release -p fkv_bench -- \
  --workload write-read --rows 20000 --batch-size 100
```

குறிகாட்டிகளில் செயல்திறன், ஒவ்வொரு நிலையிலும் தாமதம் மற்றும் உச்ச RSS ஆகியவை அடங்கும். வெளியீட்டு பணிப்பாய்வு வெளியீடு x86_64 /
aarch64க்கான `fkv_bench` பைனரி.

## RocksDB/fjall உடன் மூன்று வழி பொருத்தம்

`crate/perf/fkv_compare` அதே நிலை இயக்கி மற்றும் அதே விசை குறியாக்கத்தைப் பயன்படுத்தவும் (இறுதியில் 8-பைட் பிக்-எண்டியன் சப்ஸ்கிரிப்ட்,
அகராதி வரிசை சப்ஸ்கிரிப்ட் வரிசையுடன் ஒத்துப்போகிறது) சோதனை fkv, RocksDB, fjall: RocksDB தேர்ச்சி பெற்றது
`crate/perf/fkv_compare/cpp/rocksdb_ffi.cpp` தொகுக்கப்பட்ட பகிரப்பட்ட நூலகம் dlopen உடன் ஏற்றப்பட்டது (அதே C
ABI, Rust build ஆனது RocksDB உடன் இணைக்கப்படவில்லை), fjall நேரடியாக `fjall 3`ஐப் பயன்படுத்துகிறது. மூன்று இயந்திரங்களில் ஒவ்வொன்றும் ஒரு நூலகத்தைத் திறக்கிறது.
நிலைகளின் வரிசையில் அதே நூலகத்தில் முன்னேறவும்: மொத்த சுமை தரவை உருவாக்குகிறது, பின்னர் லென் / புள்ளி வாசிப்பு / வரம்பு வாசிப்பு /
நீக்குதல் அனைத்தும் ஒரே தரவைப் பாதிக்கும்.

```bash
cargo build --release -p fkv_compare
bash scripts/perf/build_rocksdb_ffi.sh # RocksDB இல்லை என்றால் மூன்றாவது நெடுவரிசையைத் தவிர்க்கவும்
./target/release/fkv_compare \
  --rows 25000000 --bulk-rows 25000000 --cache-bytes 268435456 \
  --readers 1,4,8,16,32 --workdir /tmp/fkv-compare \
  --rocksdb-lib target/perf/librocksdb_bench_ffi.so \
  --json /tmp/fkv-compare.json
```

முகப்புப் பக்க மேட்ரிக்ஸிற்கான எண்கள் ஒரு தடமறியும் ஓட்டத்திலிருந்து மட்டுமே வர முடியும்:

```bash
python3 scripts/perf/fkv_compare_to_js.py \
  --json /tmp/fkv-compare.json --perf-js web/src/conf/perf.js \
  --machine "..." --source "CI ரன் <id>"
```

GitHub Actions' `perf.yml` சரியாகச் செய்கிறது (`librocksdb-dev`, நிரல் அடாப்டர்களை நிறுவவும், இயக்கவும்
25M வரிசை அணி, கலைப்பொருளைப் பதிவேற்றி, `backfill=true` போது பக்கத்தை நேரடியாக நிரப்பவும்.

### திறன்

- **தரவு/கேச் விகிதம்**: 25,000,000 வரிசைகள் × 116 B ≈ 2766 MiB தரவு, ஒரு இயந்திரத்திற்கு 256 MiB கேச்,
  ≈ 11:1, 97 GiB தரவு/6 GiB கேச் (≈ 16:1) பற்றிய RocksDB இன் அதிகாரப்பூர்வ மதிப்பாய்வுடன் சீரமைக்கப்பட்டது.
- **அதே அளவு கேச்**: fkv இன் பக்க கேச் (இன்டெக்ஸ்/டேட்டா அதே பூல்), RocksDB இன் பிளாக் கேச்
  (`cache_index_and_filter_blocks=true`, தொகுதி அளவு 4 KiB), fjall இன் சொந்த தொகுதி தற்காலிக சேமிப்பு
  பட்ஜெட்கள் அனைத்தும் ஒரே எண்ணிக்கையிலான பைட்டுகளுக்கு அமைக்கப்பட்டுள்ளன.
- ** நிலைத்தன்மை காலிபர் (ஒப்பீடு நெடுவரிசை சீரமைப்பு இல்லாமல் RocksDB இயல்புநிலை உள்ளமைவைப் பயன்படுத்துகிறது)**: fkv 1× தரவு பக்கம் + ஒரு தொகுதிக்கு
  1×மேனிஃபெஸ்ட் `fdatasync` (Isomorphic to SyncData + AppendManifest of C++ EloqStore,
  இரண்டிலும் ஆஃப் சுவிட்ச் இல்லை); RocksDB நெடுவரிசை **இயல்புநிலை உள்ளமைவைப் பயன்படுத்துகிறது** (WAL on, `WriteOptions.sync=false`,
  தொடர் fsync இல்லை), fjall இயல்புநிலையையும் பயன்படுத்துகிறது (`PersistMode::Buffer`). எனவே எழுதும் கட்டம் (ஒற்றை எழுதுதல் /
  தொகுதி எழுதுதல்களுக்கு இடையிலான வேறுபாடு) ** நிலைத்தன்மையின் வலிமை வேறுபாடு**, செயல்படுத்தல் வேறுபாடு அல்ல, இது எண்ணுடன் பக்கத்தில் குறிப்பிடப்பட வேண்டும்.
  "ஒரே ஒத்திசைவு வலிமையின் கீழ் யார் வேகமாக இருக்கிறார்கள்" என்பதை நீங்கள் பகுப்பாய்வு செய்ய விரும்பினால், `--align-fsync`ஐச் சேர்க்கவும் (Sync=true உடன் RocksDB ஐத் திறக்கவும்,
  fjall SyncAll ஐப் பயன்படுத்துகிறது), இந்த விருப்பம் வெளிப்புறமாக வெளியிடப்பட்ட மெட்ரிக்குகளுக்குப் பயன்படுத்தப்படாது.
- **இரண்டு fkv இயக்கிகள்**: `--fkv-driver store` (இயல்புநிலை, செயல்பாட்டிற்குள் ஒரு `Store` உடன் நேரடியாக இணைக்கப்பட்டுள்ளது, மற்றும்
  RocksDB / fjall ஆகியவை நூலக அழைப்புகளாகும்) மற்றும் `--fkv-driver runtime` (வரிசைப்படுத்தல் முறை: ஒரு செயல்முறை
  `--fkv-shards` ஷார்ட் த்ரெட்கள், கோரிக்கைகள் விசை மூலம் அனுப்பப்படுகின்றன, C++ EloqStore இன் பொது வாசிப்பு மற்றும் எழுதுதலுடன் சீரமைக்கப்படுகின்றன
  இடைமுகம்). பிந்தையவரின் ஒவ்வொரு கோரிக்கையும் வரிசை + குறுக்கு-நூல் எழுப்புதல், நேட்டிவ் (macOS, கோப்பு IO நூல் பூல் வழியாக செல்கிறது) வழியாக செல்ல வேண்டும்.
  படிக்கும் நேரம் சுமார் 20 µs/நேரம் ஆகும், இது செயல்பாட்டில் உள்ள நேரடி இணைப்பை விட மெதுவான அளவின் வரிசையாகும்; Linux/io_uring இல் மிகவும் மலிவானது, ஆனால்
  இன்னும் ஒரு ஜம்ப். பக்க மேட்ரிக்ஸ் ஸ்டோர் காலிபரைப் பயன்படுத்துகிறது, மேலும் இயக்க நேர காலிபர் "வரிசைப்படுத்தல் படிவத்திற்கு எதிராக C++ க்கு பயன்படுத்தப்படுகிறது.
  "பொது இடைமுகத்தின்" ஒப்பீடு (fkv இயக்க நேர ஒற்றை-நூல் வாசிப்பு சுமார் 50 kops/s, C++ EloqStore FFI சிங்கிள்-த்ரெட்
  ஷார்ட் சுமார் 21 kops/s).
- **ஒத்திசைவு அளவைப் படிக்கவும்**: fkv பக்க நூல் எண் = `min(readers, --read-max-concurrency)`, இயல்புநிலை
  மேல் வரம்பு 4 (மதிப்பீட்டு இயந்திரம் vCPU உடன் சீரமைக்கப்பட்டது), **இல்லை** "ஒரு ரீடருக்கு ஒரு நூல்" - மீறப்பட்ட நிலை வரிசையை மட்டுமே அதிகரிக்கிறது;
  ஒரு நூலுக்கு கேச் = 256 MiB / நூல்களின் எண்ணிக்கை (மொத்தத் தொகை நிர்ணயிக்கப்பட்டுள்ளது, வாசகர்களுடன் துண்டாக்கப்படவில்லை) மற்றும் பயன்படுத்தப்பட்டது
  `FuturesUnordered` `--read-window` (இயல்புநிலை 16) கோரிக்கைகளை விமானத்தில் வைத்திருங்கள். RocksDB பக்கமானது
  `readers` ஒவ்வொன்றும் `std::thread` ஒரே நேரத்தில் படிக்கிறது; fjall பக்கத்தில் ஒற்றை-திரிக்கப்பட்ட வளையம் (ரீடர்ஸ் கியரைப் புறக்கணித்தல்,
  குறிப்பு நெடுவரிசையாக மட்டுமே). `--no-fkv-read-threads` "ஒற்றை இயக்க நேரத்தில் இடைப்பட்ட N ஒத்திசைவற்ற சங்கிலிகளுக்கு" மீண்டும் சிதைந்துவிடும்.
  அது பைப்லைன் ஆழம், ஒரே நேரத்தில் அல்ல, மேலும் இயந்திரங்கள் முழுவதும் ஒப்பிட முடியாது.
- **len()**: மூன்று என்ஜின்களில் எதுவும் O(1) எண்ணும் இடைமுகங்களைக் கொண்டிருக்கவில்லை. இந்த வரி முழு அட்டவணை எண்ணும் வீதமாகும், O(1) தேடல் அல்ல.
