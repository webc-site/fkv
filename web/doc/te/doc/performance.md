# పనితీరు

`fkv_bench` స్థిర కీ స్థలంలో లోడ్‌లను పరీక్షించండి, చదవండి మరియు స్కాన్ చేయండి.

```bash
cargo run --release -p fkv_bench -- \
  --workload write-read --rows 20000 --batch-size 100
```

సూచికలలో నిర్గమాంశ, ప్రతి దశలో జాప్యం మరియు గరిష్ట RSS ఉన్నాయి. విడుదల వర్క్‌ఫ్లో విడుదల x86_64 /
aarch64 కోసం `fkv_bench` బైనరీ.

## RocksDB/fjallతో మూడు-మార్గం మ్యాచ్

`crate/perf/fkv_compare` అదే స్టేజ్ డ్రైవర్ మరియు అదే కీ ఎన్‌కోడింగ్‌ని ఉపయోగించండి (చివరికి 8-బైట్ బిగ్-ఎండియన్ సబ్‌స్క్రిప్ట్,
నిఘంటువు క్రమం సబ్‌స్క్రిప్ట్ ఆర్డర్‌తో స్థిరంగా ఉంటుంది) టెస్ట్ fkv, RocksDB, fjall: RocksDB ఆమోదించబడింది
`crate/perf/fkv_compare/cpp/rocksdb_ffi.cpp` కంపైల్ చేయబడిన షేర్డ్ లైబ్రరీ dlopen (అదే C)తో లోడ్ చేయబడింది
ABI, రస్ట్ బిల్డ్ RocksDBకి లింక్ చేయదు), fjall నేరుగా `fjall 3`ని ఉపయోగిస్తుంది. మూడు ఇంజిన్లలో ప్రతి ఒక్కటి లైబ్రరీని తెరుస్తుంది.
దశల క్రమంలో అదే లైబ్రరీలో ముందుకు సాగండి: బల్క్ లోడ్ డేటాను సృష్టిస్తుంది, ఆపై లెన్ / పాయింట్ రీడింగ్ / రేంజ్ రీడింగ్ /
తొలగింపులు అన్నీ ఒకే డేటాను ప్రభావితం చేస్తాయి.

```bash
cargo build --release -p fkv_compare
bash scripts/perf/build_rocksdb_ffi.sh # RocksDB లేకపోతే మూడవ నిలువు వరుసను దాటవేయి
./target/release/fkv_compare \
  --rows 25000000 --bulk-rows 25000000 --cache-bytes 268435456 \
  --readers 1,4,8,16,32 --workdir /tmp/fkv-compare \
  --rocksdb-lib target/perf/librocksdb_bench_ffi.so \
  --json /tmp/fkv-compare.json
```

హోమ్‌పేజీ మాతృక కోసం సంఖ్యలు ఒక ట్రేస్ చేయగల రన్ నుండి మాత్రమే వస్తాయి:

```bash
python3 scripts/perf/fkv_compare_to_js.py \
  --json /tmp/fkv-compare.json --perf-js web/src/conf/perf.js \
  --machine "..." --source "CI రన్ <id>"
```

GitHub చర్యలు' `perf.yml` సరిగ్గా దీన్ని చేస్తుంది (`librocksdb-dev`, ప్రోగ్రామ్ ఎడాప్టర్‌లను ఇన్‌స్టాల్ చేయండి, అమలు చేయండి
25M అడ్డు వరుస మాతృక, కళాకృతిని అప్‌లోడ్ చేయండి మరియు `backfill=true` ఉన్నప్పుడు పేజీని నేరుగా బ్యాక్‌ఫిల్ చేయండి).

### క్యాలిబర్

- **డేటా/కాష్ నిష్పత్తి**: 25,000,000 అడ్డు వరుసలు × 116 B ≈ 2766 MiB డేటా, ఒక్కో ఇంజన్‌కు 256 MiB కాష్,
  ≈ 11:1, 97 GiB డేటా/6 GiB కాష్ (≈ 16:1) యొక్క RocksDB యొక్క అధికారిక సమీక్షతో సమలేఖనం చేయబడింది.
- **అదే మొత్తం కాష్**: fkv పేజీ కాష్ (ఇండెక్స్/డేటా అదే పూల్), RocksDB యొక్క బ్లాక్ కాష్
  (`cache_index_and_filter_blocks=true`, బ్లాక్ పరిమాణం 4 KiB), fjall యొక్క స్వంత బ్లాక్ కాష్
  బడ్జెట్‌లు అన్నీ ఒకే సంఖ్యలో బైట్‌లకు సెట్ చేయబడ్డాయి.
- ** పెర్సిస్టెన్స్ క్యాలిబర్ (పోలిక కాలమ్ సమలేఖనం లేకుండా RocksDB డిఫాల్ట్ కాన్ఫిగరేషన్‌ను ఉపయోగిస్తుంది)**: fkv 1×డేటా పేజీ + ఒక్కో బ్యాచ్‌కి
  1×మానిఫెస్ట్ `fdatasync` (ఐసోమోర్ఫిక్ టు సింక్‌డేటా + అపెండ్ మ్యానిఫెస్ట్ ఆఫ్ సి++ ఎలోక్‌స్టోర్,
  రెండింటిలోనూ ఆఫ్ స్విచ్ లేదు); RocksDB కాలమ్ **డిఫాల్ట్ కాన్ఫిగరేషన్**ని ఉపయోగిస్తుంది (WAL ఆన్, `WriteOptions.sync=false`,
  సీక్వెన్షియల్ fsync లేదు), fjall కూడా డిఫాల్ట్‌ని ఉపయోగిస్తుంది (`PersistMode::Buffer`). కాబట్టి వ్రాసే దశ (ఒకే వ్రాయడం /
  బ్యాచ్ వ్రాతల మధ్య వ్యత్యాసం) **పట్టుదల బలం తేడా**, అమలు వ్యత్యాసం కాదు, ఇది తప్పనిసరిగా పేజీలో సంఖ్యతో పాటు పేర్కొనాలి.
  మీరు "అదే సమకాలీకరణ బలం కింద ఎవరు వేగంగా ఉన్నారు" అని విశ్లేషించాలనుకుంటే, `--align-fsync`ని జోడించండి (Sync=trueతో RocksDBని తెరవండి,
  fjall SyncAllని ఉపయోగిస్తుంది), ఈ ఐచ్ఛికం బాహ్యంగా ప్రచురించబడిన మాత్రికల కోసం ఉపయోగించబడదు.
- **రెండు fkv డ్రైవర్లు**: `--fkv-driver store` (డిఫాల్ట్, ప్రాసెస్‌లో నేరుగా ఒకే `Store`కి కనెక్ట్ చేయబడింది మరియు
  RocksDB / fjall కూడా లైబ్రరీ కాల్‌లు) మరియు `--fkv-driver runtime` (డిప్లాయ్‌మెంట్ మోడ్: ఒక ప్రక్రియ
  `--fkv-shards` షార్డ్ థ్రెడ్‌లు, అభ్యర్థనలు కీ ద్వారా రూట్ చేయబడతాయి, C++ EloqStore యొక్క పబ్లిక్ రీడింగ్ మరియు రైటింగ్‌తో సమలేఖనం చేయబడతాయి
  ఇంటర్ఫేస్). తరువాతి ప్రతి అభ్యర్థన క్యూ + క్రాస్-థ్రెడ్ వేక్-అప్, స్థానిక (macOS, ఫైల్ IO థ్రెడ్ పూల్ గుండా వెళుతుంది) ద్వారా వెళ్లాలి.
  పఠన సమయం దాదాపు 20 µs/సమయం, ఇది ఇన్-ప్రాసెస్ డైరెక్ట్ కనెక్షన్ కంటే నెమ్మదిగా ఉండే క్రమం; Linux/io_uringలో చాలా తక్కువ ధర, కానీ
  ఇంకా జంప్. పేజీ మ్యాట్రిక్స్ స్టోర్ క్యాలిబర్‌ని ఉపయోగిస్తుంది మరియు రన్‌టైమ్ క్యాలిబర్ "డిప్లాయ్‌మెంట్ ఫారమ్ vs C++ కోసం ఉపయోగించబడుతుంది.
  "పబ్లిక్ ఇంటర్‌ఫేస్" యొక్క పోలిక (fkv రన్‌టైమ్ సింగిల్-థ్రెడ్ రీడింగ్ దాదాపు 50 kops/s, C++ EloqStore FFI సింగిల్-థ్రెడ్
  షార్డ్ సుమారు 21 కోప్స్/సె).
- **కరెన్సీ క్యాలిబర్‌ని చదవండి**: fkv సైడ్ థ్రెడ్ నంబర్ = `min(readers, --read-max-concurrency)`, డిఫాల్ట్
  ఎగువ పరిమితి 4 (మూల్యాంకన యంత్రం vCPUతో సమలేఖనం చేయబడింది), ** కాదు ** "ఒక రీడర్‌కు ఒక థ్రెడ్" - మించిపోయిన స్థాయి క్యూను మాత్రమే పెంచుతుంది;
  ఒక్కో థ్రెడ్‌కు కాష్ = 256 MiB / థ్రెడ్‌ల సంఖ్య (మొత్తం మొత్తం నిర్ణయించబడింది, రీడర్‌లతో షేడ్ చేయబడదు) మరియు ఉపయోగించబడుతుంది
  ఫ్లైలో `FuturesUnordered` `--read-window` (డిఫాల్ట్ 16) అభ్యర్థనలను ఉంచండి. RocksDB వైపు ఉంది
  `readers` ప్రతి `std::thread` ఏకకాలంలో చదువుతుంది; fjall వైపు సింగిల్-థ్రెడ్ లూప్ (రీడర్స్ గేర్‌ను విస్మరించడం,
  రిఫరెన్స్ కాలమ్‌గా మాత్రమే). `--no-fkv-read-threads` "ఒకే రన్‌టైమ్‌లో ఇంటర్‌లీవ్డ్ N అసమకాలిక గొలుసులకు" తిరిగి క్షీణించవచ్చు.
  అది పైప్‌లైన్ డెప్త్, కాన్కరెన్సీ కాదు మరియు ఇంజిన్‌లలో పోల్చదగినది కాదు.
- **len()**: మూడు ఇంజిన్‌లలో ఏదీ O(1) కౌంటింగ్ ఇంటర్‌ఫేస్‌లను కలిగి లేదు. ఈ పంక్తి పూర్తి పట్టిక లెక్కింపు రేటు, O(1) లుక్అప్ కాదు.
