# ביצועים

`fkv_bench` בדוק עומסי כתיבה, קריאה וסריקה על שטח מפתח קבוע.

```bash
cargo run --release -p fkv_bench -- \
  --workload write-read --rows 20000 --batch-size 100
```

האינדיקטורים כוללים תפוקה, חביון בכל שלב ושיא RSS. שחרור זרימת עבודה מהדורת x86_64 /
`fkv_bench` בינארי עבור aarch64.

## התאמה תלת כיוונית עם RocksDB/fjall

`crate/perf/fkv_compare` השתמש באותו מנהל התקן שלב ובאותו קידוד מפתח (8-בתים מנוי big-endian בסוף,
סדר המילון עולה בקנה אחד עם סדר הכתוביות) מבחן fkv, RocksDB, fjall: RocksDB עבר
`crate/perf/fkv_compare/cpp/rocksdb_ffi.cpp` הספרייה המשותפת המהודר נטענת עם dlopen (אותו C
ABI, Rust build לא מקשר ל- RocksDB), fjall משתמש ב`fjall 3` ישירות. כל אחד משלושת המנועים פותח ספרייה.
התקדמות על אותה ספרייה בסדר שלבים: עומס בכמות גדולה יוצר נתונים, ולאחר מכן קריאה נקודתית / קריאת טווח /
המחיקות כולן משפיעות על אותם נתונים.

```bash
cargo build --release -p fkv_compare
bash scripts/perf/build_rocksdb_ffi.sh # דלג על העמודה השלישית אם אין RocksDB
./target/release/fkv_compare \
  --rows 25000000 --bulk-rows 25000000 --cache-bytes 268435456 \
  --readers 1,4,8,16,32 --workdir /tmp/fkv-compare \
  --rocksdb-lib target/perf/librocksdb_bench_ffi.so \
  --json /tmp/fkv-compare.json
```

המספרים עבור מטריצת דף הבית יכולים להגיע רק מהפעלה אחת ניתנת למעקב:

```bash
python3 scripts/perf/fkv_compare_to_js.py \
  --json /tmp/fkv-compare.json --perf-js web/src/conf/perf.js \
  --מכונה "..." --מקור "CI run <id>"
```

`perf.yml` של GitHub Actions עושה בדיוק את זה (התקן את `librocksdb-dev`, מתאמי תוכנה, הפעל
מטריצת שורות של 25 מיליון, העלה חפץ ומלא ישירות את הדף כאשר `backfill=true`).

### קָלִיבֶּר

- **יחס נתונים/מטמון**: 25,000,000 שורות × 116 B ≈ 2766 MiB של נתונים, 256 MiB של מטמון לכל מנוע,
  ≈ 11:1, מיושר עם הסקירה הרשמית של RocksDB של 97 נתוני GiB/6 GiB מטמון (≈ 16:1).
- **אותה כמות מטמון**: מטמון הדפים של fkv (אינדקס/נתונים אותו מאגר), מטמון הבלוק של RocksDB
  (`cache_index_and_filter_blocks=true`, בלוק בגודל 4 KiB), מטמון הבלוק של fjall עצמו
  התקציבים כולם מוגדרים לאותו מספר בתים.
- **קליבר התמדה (עמודת ההשוואה משתמשת בתצורת ברירת המחדל של RocksDB, ללא יישור)**: fkv 1×דף נתונים + לכל אצווה
  1×manifest `fdatasync` (Isomorphic to SyncData + AppendManifest של C++ EloqStore,
  לשניהם אין מתג כיבוי); העמודה RocksDB משתמשת ב**תצורת ברירת המחדל** (WAL on, `WriteOptions.sync=false`,
  אין fsync רציף), fjall משתמש גם בברירת המחדל (`PersistMode::Buffer`). לכן שלב הכתיבה (כתיבה בודדת /
  ההבדל בין כתבי אצווה) הוא **הפרש חוזק ההתמדה**, לא ההבדל ביישום, אותו יש לציין בעמוד יחד עם המספר.
  אם אתה רוצה לנתח "מי מהיר יותר באותה חוזק סנכרון", הוסף את `--align-fsync` (פתח את RocksDB עם sync=true,
  fjall משתמש ב-SyncAll), אפשרות זו אינה משמשת עבור מטריצות שפורסמו חיצונית.
- **שני מנהלי התקנים של fkv**: `--fkv-driver store` (ברירת מחדל, מחובר ישירות ל`Store` יחיד בתוך התהליך, וכן
  RocksDB / fjall הם גם שיחות ספרייה) ו`--fkv-driver runtime` (מצב פריסה: תהליך
  `--fkv-shards` שרשורי רסיס, בקשות מנותבות לפי מפתח, מיושרים לקריאה וכתיבה ציבורית של C++ EloqStore
  מִמְשָׁק). כל בקשה של האחרון צריכה לעבור דרך התור + התעוררות חוצה חוטים, מקורית (macOS, קובץ IO עובר במאגר השרשורים)
  זמן הקריאה הוא בערך 20 מיקרוסופט לזמן, שהוא איטי בסדר גודל מחיבור ישיר בתהליך; הרבה יותר זול ב-Linux/io_uring, אבל
  עדיין קפיצה. מטריצת העמוד משתמשת בקליבר החנות, וקליבר זמן הריצה משמש עבור "טופס פריסה לעומת C++
  השוואה של "ממשק ציבורי" (קריאה של זמן ריצה עם חוט בודד הוא כ-50 קופס/שנייה, C++ EloqStore FFI חוט יחיד
  רסיס כ-21 קופס/שניה).
- **קרא קליבר מקביל**: מספר חוט בצד fkv = `min(readers, --read-max-concurrency)`, ברירת מחדל
  הגבול העליון הוא 4 (מיושר ל-vCPU של מכונת ההערכה), **לא** "שרשור אחד לכל קורא" - הרמה החורגת רק מגדילה את התור;
  מטמון לכל שרשור = 256 MiB / מספר שרשורים (הסכום הכולל קבוע, לא מגורר עם הקוראים), ומשמש
  `FuturesUnordered` שמור `--read-window` (ברירת מחדל 16) בקשות בזמן. הצד של RocksDB הוא
  `readers` כל `std::thread` קורא בו-זמנית; לולאה עם הברגה בודדת בצד הר (מתעלם מציוד הקוראים,
  כעמודת התייחסות בלבד). `--no-fkv-read-threads` יכול להתדרדר בחזרה ל"שרשראות א-סינכרוניות N משולבות בזמן ריצה בודד".
  זהו עומק הצינור, לא במקביל, ואינו בר השוואה בין מנועים.
- **len()**: לאף אחד משלושת המנועים אין ממשקי ספירת O(1). שורה זו היא קצב ספירת הטבלה המלאה, לא בדיקת O(1).
