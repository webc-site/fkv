# Արտադրողականություն

`fkv_bench` Ստուգեք գրելու, կարդալու և սկանավորելու բեռները ֆիքսված ստեղնաշարի վրա:

```bash
cargo run --release -p fkv_bench -- \
  --workload write-read --rows 20000 --batch-size 100
```

Ցուցանիշները ներառում են թողունակությունը, ուշացումը յուրաքանչյուր փուլում և առավելագույն RSS: աշխատանքի հոսքի թողարկում x86_64 /
`fkv_bench` երկուական aarch64-ի համար:

## Եռակողմ համադրում RocksDB/fjall-ի հետ

`crate/perf/fkv_compare` Օգտագործեք նույն փուլի դրայվերը և նույն ստեղնաշարի կոդավորումը (8 բայթ մեծ էնդյան բաժանորդ վերջում,
Բառարանի կարգը համապատասխանում է բաժանորդագրության կարգին) Փորձարկել fkv, RocksDB, fjall. RocksDB-ն անցել է
`crate/perf/fkv_compare/cpp/rocksdb_ffi.cpp` Կազմված ընդհանուր գրադարանը բեռնված է dlopen-ով (նույն C
ABI, Rust build-ը չի կապում RocksDB-ին), fjall-ն ուղղակիորեն օգտագործում է `fjall 3`: Երեք շարժիչներից յուրաքանչյուրը բացում է գրադարան:
Միևնույն գրադարանում առաջ շարժվեք փուլերի հերթականությամբ. զանգվածային բեռնվածությունը ստեղծում է տվյալներ, այնուհետև len / կետի ընթերցում / տիրույթի ընթերցում /
Բոլոր ջնջումները ազդում են նույն տվյալների վրա:

```bash
cargo build --release -p fkv_compare
bash scripts/perf/build_rocksdb_ffi.sh # Բաց թողնել երրորդ սյունակը, եթե RocksDB չկա
./target/release/fkv_compare \
  --rows 25000000 --bulk-rows 25000000 --cache-bytes 268435456 \
  --readers 1,4,8,16,32 --workdir /tmp/fkv-compare \
  --rocksdb-lib target/perf/librocksdb_bench_ffi.so \
  --json /tmp/fkv-compare.json
```

Գլխավոր էջի մատրիցայի համարները կարող են առաջանալ միայն մեկ հետագծելի գործարկումից.

```bash
python3 scripts/perf/fkv_compare_to_js.py \
  --json /tmp/fkv-compare.json --perf-js web/src/conf/perf.js \
  --machine "..." --աղբյուրը "CI run <id>"
```

GitHub Actions-ի `perf.yml`-ն անում է հենց դա (տեղադրել `librocksdb-dev`, ծրագրի ադապտերներ, գործարկել
25M տողերի մատրիցա, վերբեռնեք արտեֆակտ և ուղղակիորեն լրացրեք էջը, երբ `backfill=true`):

### տրամաչափ

- **Տվյալների/Քեշի հարաբերակցությունը**՝ 25,000,000 տող × 116 B ≈ 2766 ՄԲ տվյալների, 256 ՄԲ քեշ մեկ շարժիչի համար,
  ≈ 11:1, համահունչ RocksDB-ի 97 GiB տվյալների/6 GiB քեշի պաշտոնական ակնարկին (≈ 16:1):
- **Քեշի նույն քանակությունը**՝ fkv-ի էջի քեշը (ինդեքսը/տվյալների նույն լողավազանը), RocksDB-ի բլոկ քեշը
  (`cache_index_and_filter_blocks=true`, բլոկի չափը 4 ԿԲ), fjall-ի սեփական բլոկ քեշը
  Բյուջեները բոլորը սահմանված են նույն թվով բայթերի համար:
- **Հաստատակամության տրամաչափ (համեմատության սյունակում օգտագործվում է RocksDB լռելյայն կոնֆիգուրացիան, առանց հավասարեցման)**. fkv 1×տվյալների էջ + յուրաքանչյուր խմբաքանակի համար
  1×մանիֆեստ `fdatasync` (Isomorphic to SyncData + AppendManifest of C++ EloqStore,
  Ոչ մեկը չունի անջատիչ); RocksDB սյունակը օգտագործում է **կանխադրված կոնֆիգուրացիան** (WAL միացված է, `WriteOptions.sync=false`,
  Ոչ մի հաջորդական fsync), fjall-ը նաև օգտագործում է լռելյայն (`PersistMode::Buffer`): Հետևաբար գրելու փուլը (մեկ գրություն /
  Խմբաքանակի գրումների միջև տարբերությունը **համառության ուժի տարբերությունն է**, այլ ոչ թե կատարման տարբերությունը, որը պետք է նշված լինի էջում թվի հետ միասին:
  Եթե ​​ցանկանում եք վերլուծել «ով է ավելի արագ նույն համաժամացման հզորության ներքո», ավելացրեք `--align-fsync` (բացեք RocksDB-ը sync=true-ով,
  fjall-ն օգտագործում է SyncAll), այս տարբերակը չի օգտագործվում արտաքին հրապարակված մատրիցների համար։
- **Երկու fkv դրայվեր **՝ `--fkv-driver store` (կանխադրված, ուղղակիորեն կապված է մեկ `Store` գործընթացում, և
  RocksDB / fjall-ը նաև գրադարանային զանգեր են) և `--fkv-driver runtime` (տեղակայման ռեժիմ. գործընթաց
  `--fkv-shards` բեկորային շղթաներ, հարցումները ուղղորդվում են բանալիով, համահունչ C++ EloqStore-ի հանրային ընթերցման և գրելու հետ:
  ինտերֆեյս): Վերջինիս յուրաքանչյուր խնդրանք պետք է անցնի հերթով + խաչաձեւ շղթայական արթնացում, բնիկ (macOS, ֆայլի IO-ն անցնում է thread pool-ով)
  Ընթերցանության ժամանակը մոտ 20 µs/ժամ է, ինչը մեծության կարգով ավելի դանդաղ է, քան ընթացքի մեջ գտնվող ուղիղ միացումը. շատ ավելի էժան Linux/io_uring-ում, բայց
  Դեռ ցատկ. Էջի մատրիցը օգտագործում է խանութի տրամաչափը, իսկ գործարկման ժամանակի տրամաչափը օգտագործվում է «տեղակայման ձևն ընդդեմ C++-ի»
  «Հանրային ինտերֆեյսի» համեմատություն (fkv գործարկման մեկ շղթայի ընթերցումը մոտ 50 կոպ/վ է, C++ EloqStore FFI մեկ թեմա
  բեկոր մոտ 21 կոպ/վ):
- **Կարդալ համաժամանակյա տրամաչափը**. fkv կողային շղթայի համարը = `min(readers, --read-max-concurrency)`, լռելյայն
  Վերին սահմանը 4 է (համապատասխանեցված vCPU գնահատման մեքենայի հետ), **ոչ** «մեկ թեմա յուրաքանչյուր ընթերցողի համար» - գերազանցված մակարդակը միայն մեծացնում է հերթը.
  Քեշը մեկ շղթայի համար = 256 ՄԲ / թելերի քանակը (ընդհանուր գումարը ֆիքսված է, չի մանրացված ընթերցողների հետ) և օգտագործվում է
  `FuturesUnordered` Պահպանեք `--read-window` (կանխադրված 16) հարցումները: RocksDB կողմն է
  `readers` Յուրաքանչյուր `std::thread` կարդում է միաժամանակ; մեկ թելերով հանգույց fjall-ի կողմից (անտեսելով ընթերցողների հանդերձանքը,
  Միայն որպես հղման սյունակ): `--no-fkv-read-threads`-ը կարող է հետ դառնալ «խճճված N ասինխրոն շղթաներ մեկ գործարկման ժամանակ»:
  Դա խողովակաշարի խորությունն է, ոչ համաժամանակյա, և համեմատելի չէ շարժիչների միջև:
- **len()**. երեք շարժիչներից և ոչ մեկը չունի O(1) հաշվելու միջերես: Այս տողը աղյուսակի ամբողջական հաշվման արագությունն է, այլ ոչ թե O(1) որոնումը:
