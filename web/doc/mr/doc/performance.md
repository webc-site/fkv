# कामगिरी

`fkv_bench` निश्चित की स्पेसवर चाचणी लिहा, वाचा आणि लोड स्कॅन करा.

```bash
cargo run --release -p fkv_bench -- \
  --workload write-read --rows 20000 --batch-size 100
```

निर्देशकांमध्ये थ्रूपुट, प्रत्येक टप्प्यावर विलंबता आणि शिखर RSS समाविष्ट आहे. रिलीझ वर्कफ्लो रिलीज x86_64 /
aarch64 साठी `fkv_bench` बायनरी.

## RocksDB/fjall सह थ्री-वे मॅचअप

`crate/perf/fkv_compare` समान स्टेज ड्रायव्हर आणि समान की एन्कोडिंग वापरा (शेवटी 8-बाइट बिग-एंडियन सबस्क्रिप्ट,
डिक्शनरी ऑर्डर सबस्क्रिप्ट ऑर्डरशी सुसंगत आहे) चाचणी fkv, RocksDB, fjall: RocksDB उत्तीर्ण
`crate/perf/fkv_compare/cpp/rocksdb_ffi.cpp` संकलित सामायिक लायब्ररी dlopen ने लोड केली आहे (समान C
ABI, Rust बिल्ड RocksDB शी लिंक करत नाही), fjall थेट `fjall 3` वापरते. तीन इंजिनांपैकी प्रत्येक एक लायब्ररी उघडते.
टप्प्यांच्या क्रमाने समान लायब्ररीवर प्रगती करा: मोठ्या प्रमाणात लोड डेटा तयार करतो आणि नंतर लेन / पॉइंट वाचन / श्रेणी वाचन /
सर्व हटवण्यामुळे समान डेटावर परिणाम होतो.

```bash
cargo build --release -p fkv_compare
bash scripts/perf/build_rocksdb_ffi.sh # RocksDB नसल्यास तिसरा स्तंभ वगळा
./target/release/fkv_compare \
  --rows 25000000 --bulk-rows 25000000 --cache-bytes 268435456 \
  --readers 1,4,8,16,32 --workdir /tmp/fkv-compare \
  --rocksdb-lib target/perf/librocksdb_bench_ffi.so \
  --json /tmp/fkv-compare.json
```

मुख्यपृष्ठ मॅट्रिक्ससाठी संख्या फक्त एका शोधण्यायोग्य रनमधून येऊ शकतात:

```bash
python3 scripts/perf/fkv_compare_to_js.py \
  --json /tmp/fkv-compare.json --perf-js web/src/conf/perf.js \
  --मशीन "..." --स्रोत "CI रन <id>"
```

GitHub क्रिया' `perf.yml` नेमके हेच करते (`librocksdb-dev` स्थापित करा, प्रोग्राम ॲडॉप्टर, चालवा
25M पंक्ती मॅट्रिक्स, आर्टिफॅक्ट अपलोड करा आणि जेव्हा `backfill=true` पृष्ठ थेट बॅकफिल करा).

### कॅलिबर

- **डेटा/कॅशे रेशो**: २५,०००,००० पंक्ती × ११६ बी ≈ २७६६ MiB डेटा, २५६ MiB कॅशे प्रति इंजिन,
  ≈ 11:1, 97 GiB डेटा/6 GiB कॅशे (≈ 16:1) च्या RocksDB च्या अधिकृत पुनरावलोकनासह संरेखित.
- **समान कॅशे**: fkv चे पेज कॅशे (इंडेक्स/डेटा समान पूल), RocksDB चे ब्लॉक कॅशे
  (`cache_index_and_filter_blocks=true`, ब्लॉक आकार 4 KiB), fjall चे स्वतःचे ब्लॉक कॅशे
  बजेट सर्व समान बाइट्सवर सेट केलेले आहेत.
- **परसिस्टन्स कॅलिबर (तुलना स्तंभ RocksDB डीफॉल्ट कॉन्फिगरेशन वापरतो, संरेखन न करता)**: fkv 1×डेटा पृष्ठ + प्रति बॅच
  1×मॅनिफेस्ट `fdatasync` (Isomorphic to SyncData + AppendManifest of C++ EloqStore,
  दोन्हीकडे बंद स्विच नाही); RocksDB स्तंभ **डीफॉल्ट कॉन्फिगरेशन** वापरतो (WAL चालू, `WriteOptions.sync=false`,
  कोणतेही अनुक्रमिक fsync नाही), fjall देखील डीफॉल्ट वापरते (`PersistMode::Buffer`). म्हणून लेखन टप्पा (एकल लेखन /
  बॅच राइट) मधील फरक हा **सिस्टन्स स्ट्रेंथ फरक** आहे, अंमलबजावणीतील फरक नाही, जो नंबरसह पृष्ठावर नमूद करणे आवश्यक आहे.
  तुम्हाला "समान सिंक्रोनाइझेशन ताकदीखाली कोण वेगवान आहे" याचे विश्लेषण करायचे असल्यास, `--align-fsync` जोडा (sync=true सह RocksDB उघडा,
  fjall SyncAll वापरते), हा पर्याय बाहेरून प्रकाशित मॅट्रिक्ससाठी वापरला जात नाही.
- **दोन fkv ड्रायव्हर्स**: `--fkv-driver store` (डीफॉल्ट, प्रक्रियेत थेट एका `Store`शी कनेक्ट केलेले, आणि
  RocksDB / fjall हे लायब्ररी कॉल देखील आहेत) आणि `--fkv-driver runtime` (उपयोजन मोड: एक प्रक्रिया
  `--fkv-shards` शार्ड थ्रेड्स, विनंत्या की द्वारे रूट केल्या जातात, C++ EloqStore च्या सार्वजनिक वाचन आणि लेखनासह संरेखित केल्या जातात
  इंटरफेस). नंतरच्या प्रत्येक विनंतीला रांगेतून जाणे आवश्यक आहे + क्रॉस-थ्रेड वेक-अप, नेटिव्ह (macOS, फाइल IO थ्रेड पूलमधून जाते)
  वाचन वेळ सुमारे 20 µs/वेळ आहे, जी प्रक्रिया-प्रक्रियेत थेट कनेक्शनपेक्षा हळू हळू आहे; Linux/io_uring वर खूप स्वस्त, पण
  तरीही एक उडी. पेज मॅट्रिक्स स्टोअर कॅलिबर वापरते आणि रनटाइम कॅलिबर "डिप्लॉयमेंट फॉर्म विरुद्ध C++" साठी वापरले जाते.
  "पब्लिक इंटरफेस" ची तुलना (fkv रनटाइम सिंगल-थ्रेड रीडिंग सुमारे 50 kops/s आहे, C++ EloqStore FFI सिंगल-थ्रेड
  शार्ड सुमारे 21 kops/s).
- **कंकरन्सी कॅलिबर वाचा**: fkv साइड थ्रेड नंबर = `min(readers, --read-max-concurrency)`, डीफॉल्ट
  वरची मर्यादा 4 आहे (मूल्यांकन मशीन vCPU सह संरेखित), ** नाही** "एक थ्रेड प्रति वाचक" - ओलांडलेली पातळी केवळ रांग वाढवते;
  कॅशे प्रति थ्रेड = 256 MiB / थ्रेडची संख्या (एकूण रक्कम निश्चित केली आहे, वाचकांसह तुकडे केलेली नाही), आणि वापरली
  `FuturesUnordered` फ्लायवर `--read-window` (डिफॉल्ट 16) विनंत्या ठेवा. RocksDB बाजू आहे
  `readers` प्रत्येक `std::thread` एकाच वेळी वाचतो; fjall बाजूला सिंगल-थ्रेडेड लूप (वाचकांच्या गियरकडे दुर्लक्ष करून,
  फक्त संदर्भ स्तंभ म्हणून). `--no-fkv-read-threads` "एकाच रनटाइमवर इंटरलीव्हड N असिंक्रोनस चेन" वर परत येऊ शकते.
  ती पाइपलाइनची खोली आहे, एकरूपता नाही आणि सर्व इंजिनांमध्ये तुलना करता येत नाही.
- **len():**: तीन इंजिनांपैकी कोणत्याही इंजिनमध्ये O(1) मोजणी इंटरफेस नाहीत. ही ओळ संपूर्ण सारणी मोजणी दर आहे, O(1) लुकअप नाही.
