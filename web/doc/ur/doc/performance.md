# کارکردگی

`fkv_bench` ایک مقررہ کلیدی جگہ پر بوجھ لکھنے، پڑھنے اور اسکین کرنے کی جانچ کریں۔

```bash
cargo run --release -p fkv_bench -- \
  --workload write-read --rows 20000 --batch-size 100
```

اشارے میں تھرو پٹ، ہر مرحلے میں تاخیر، اور چوٹی RSS شامل ہیں۔ ریلیز ورک فلو ریلیز x86_64 /
`fkv_bench` بائنری برائے aarch64۔

## RocksDB/fjall کے ساتھ تین طرفہ میچ اپ

`crate/perf/fkv_compare` ایک ہی اسٹیج ڈرائیور اور وہی کلیدی انکوڈنگ استعمال کریں (آخر میں 8 بائٹ بگ اینڈین سبسکرپٹ،
ڈکشنری آرڈر سب اسکرپٹ آرڈر کے ساتھ مطابقت رکھتا ہے) ٹیسٹ fkv, RocksDB, fjall: RocksDB پاس
`crate/perf/fkv_compare/cpp/rocksdb_ffi.cpp` مرتب کردہ مشترکہ لائبریری dlopen کے ساتھ بھری ہوئی ہے (وہی C
ABI، Rust build RocksDB سے منسلک نہیں ہے، fjall براہ راست `fjall 3` استعمال کرتا ہے۔ تین انجنوں میں سے ہر ایک لائبریری کھولتا ہے۔
مراحل کی ترتیب میں ایک ہی لائبریری پر پیش قدمی: بلک لوڈ ڈیٹا بناتا ہے، اور پھر لین/پوائنٹ ریڈنگ/رینج ریڈنگ/
حذف کرنے سے سبھی ایک ہی ڈیٹا کو متاثر کرتے ہیں۔

```bash
cargo build --release -p fkv_compare
bash scripts/perf/build_rocksdb_ffi.sh # اگر کوئی RocksDB نہیں ہے تو تیسرا کالم چھوڑ دیں
./target/release/fkv_compare \
  --rows 25000000 --bulk-rows 25000000 --cache-bytes 268435456 \
  --readers 1,4,8,16,32 --workdir /tmp/fkv-compare \
  --rocksdb-lib target/perf/librocksdb_bench_ffi.so \
  --json /tmp/fkv-compare.json
```

ہوم پیج میٹرکس کے نمبر صرف ایک ٹریس ایبل رن سے آ سکتے ہیں:

```bash
python3 scripts/perf/fkv_compare_to_js.py \
  --json /tmp/fkv-compare.json --perf-js web/src/conf/perf.js \
  --machine "..." --source "CI رن <id>"
```

GitHub ایکشنز '`perf.yml` بالکل ایسا ہی کرتا ہے (انسٹال `librocksdb-dev`، پروگرام اڈاپٹر، چلائیں
25M قطار میٹرکس، آرٹفیکٹ اپ لوڈ کریں، اور صفحہ کو براہ راست بیک فل کریں جب `backfill=true`)۔

### صلاحیت

- **ڈیٹا/کیشے کا تناسب**: 25,000,000 قطاریں × 116 B ≈ 2766 MiB ڈیٹا، 256 MiB کیشے فی انجن،
  ≈ 11:1، RocksDB کے 97 GiB ڈیٹا/6 GiB کیشے (≈ 16:1) کے سرکاری جائزے کے ساتھ منسلک۔
- **کیشے کی ایک ہی مقدار**: fkv کا صفحہ کیشے (انڈیکس/ڈیٹا ایک ہی پول)، RocksDB کا بلاک کیش
  (`cache_index_and_filter_blocks=true`، بلاک سائز 4 KiB)، fjall کا اپنا بلاک کیش
  بجٹ سبھی بائٹس کی ایک ہی تعداد پر سیٹ ہیں۔
- **پرسسٹینس کیلیبر (موازنہ کالم RocksDB ڈیفالٹ کنفیگریشن کا استعمال کرتا ہے، بغیر سیدھ کے)**: fkv 1×ڈیٹا پیج + فی بیچ
  1×مینیفسٹ `fdatasync` (Isomorphic to SyncData + AppendManifest of C++ EloqStore،
  نہ ہی کوئی آف سوئچ ہے) RocksDB کالم **ڈیفالٹ کنفیگریشن** استعمال کرتا ہے (WAL on, `WriteOptions.sync=false`،
  کوئی ترتیب وار fsync نہیں ہے، fjall ڈیفالٹ (`PersistMode::Buffer`) بھی استعمال کرتا ہے۔ لہذا لکھنے کا مرحلہ (واحد تحریر /
  بیچ لکھنے کے درمیان فرق) **استقامت کی طاقت کا فرق** ہے، نفاذ کا فرق نہیں، جسے صفحہ پر نمبر کے ساتھ بیان کرنا ضروری ہے۔
  اگر آپ تجزیہ کرنا چاہتے ہیں کہ "ایک ہی مطابقت پذیری کی طاقت کے تحت کون تیز تر ہے"، شامل کریں `--align-fsync` (کھولیں RocksDB with sync=true،
  fjall SyncAll استعمال کرتا ہے)، یہ اختیار بیرونی طور پر شائع شدہ میٹرکس کے لیے استعمال نہیں ہوتا ہے۔
- **دو fkv ڈرائیور**: `--fkv-driver store` (پہلے سے طے شدہ، عمل کے اندر براہ راست ایک سنگل `Store` سے منسلک، اور
  RocksDB / fjall لائبریری کالز بھی ہیں) اور `--fkv-driver runtime` (تعیناتی موڈ: ایک عمل
  `--fkv-shards` شارڈ تھریڈز، درخواستوں کو کلید کے ذریعے روٹ کیا جاتا ہے، C++ EloqStore کی عوامی پڑھنے اور تحریر کے ساتھ منسلک ہوتا ہے۔
  انٹرفیس)۔ مؤخر الذکر کی ہر درخواست کو قطار + کراس تھریڈ ویک اپ، مقامی (macOS، فائل IO تھریڈ پول سے گزرنے کی ضرورت ہے)
  پڑھنے کا وقت تقریباً 20 µs/وقت ہے، جو کہ عمل میں براہ راست کنکشن کے مقابلے میں سست رفتار کا حکم ہے۔ لینکس/io_uring پر بہت سستا، لیکن
  اب بھی ایک چھلانگ۔ صفحہ میٹرکس اسٹور کیلیبر کا استعمال کرتا ہے، اور رن ٹائم کیلیبر کو "تعیناتی فارم بمقابلہ C++" کے لیے استعمال کیا جاتا ہے۔
  "پبلک انٹرفیس" کا موازنہ (fkv رن ٹائم سنگل تھریڈ ریڈنگ تقریباً 50 kops/s ہے، C++ EloqStore FFI سنگل تھریڈ
  شارڈ تقریباً 21 کوپس فی سیکنڈ)۔
- **کنکرنسی کیلیبر پڑھیں**: fkv سائیڈ تھریڈ نمبر = `min(readers, --read-max-concurrency)`، ڈیفالٹ
  اوپری حد 4 ہے (تشخیصی مشین vCPU کے ساتھ منسلک)، **نہیں** "ایک دھاگہ فی ریڈر" - حد سے تجاوز صرف قطار کو بڑھاتا ہے۔
  کیش فی تھریڈ = 256 MiB / دھاگوں کی تعداد (کل رقم مقرر ہے، قارئین کے ساتھ کٹا ہوا نہیں)، اور استعمال کیا جاتا ہے
  `FuturesUnordered` `--read-window` (پہلے سے طے شدہ 16) درخواستوں کو فلائی پر رکھیں۔ RocksDB طرف ہے
  `readers` ہر ایک `std::thread` بیک وقت پڑھتا ہے۔ fjall سائیڈ پر سنگل تھریڈڈ لوپ (قارئین کے گیئر کو نظر انداز کرتے ہوئے،
  صرف ایک حوالہ کالم کے طور پر)۔ `--no-fkv-read-threads` واپس "ایک ہی رن ٹائم پر انٹرلیویڈ N غیر مطابقت پذیر زنجیروں" میں تبدیل ہو سکتا ہے۔
  یہ پائپ لائن کی گہرائی ہے، ہم آہنگی نہیں، اور انجنوں میں موازنہ نہیں ہے۔
- **len()**: تین انجنوں میں سے کسی میں بھی O(1) گنتی کے انٹرفیس نہیں ہیں۔ یہ لائن مکمل ٹیبل گنتی کی شرح ہے، O(1) تلاش نہیں ہے۔
