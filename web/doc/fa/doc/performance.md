# عملکرد

`fkv_bench` بارهای نوشتن، خواندن و اسکن را روی یک فضای کلید ثابت آزمایش کنید.

```bash
cargo run --release -p fkv_bench -- \
  --workload write-read --rows 20000 --batch-size 100
```

شاخص ها شامل توان عملیاتی، تأخیر در هر مرحله و پیک RSS است. انتشار جریان کار انتشار x86_64 /
`fkv_bench` باینری برای aarch64.

## تطبیق سه طرفه با RocksDB/fjall

`crate/perf/fkv_compare` از همان درایور مرحله و رمزگذاری کلید یکسان (8 بایت زیرنویس big-endian در پایان،
ترتیب دیکشنری با ترتیب زیرنویس سازگار است) تست fkv، RocksDB، fjall: RocksDB قبول شد
`crate/perf/fkv_compare/cpp/rocksdb_ffi.cpp` کتابخانه مشترک کامپایل شده با dlopen بارگیری می شود (همان C
ABI، Rust build به RocksDB پیوند نمی‌خورد)، fjall مستقیماً از `fjall 3` استفاده می‌کند. هر یک از این سه موتور یک کتابخانه باز می کند.
در همان کتابخانه به ترتیب مراحل پیش بروید: بار انبوه داده ها را ایجاد می کند و سپس len / نقطه خواندن / خواندن محدوده /
حذف ها همگی روی داده های یکسانی تأثیر می گذارند.

```bash
cargo build --release -p fkv_compare
bash scripts/perf/build_rocksdb_ffi.sh # اگر RocksDB وجود ندارد از ستون سوم رد شوید
./target/release/fkv_compare \
  --rows 25000000 --bulk-rows 25000000 --cache-bytes 268435456 \
  --readers 1,4,8,16,32 --workdir /tmp/fkv-compare \
  --rocksdb-lib target/perf/librocksdb_bench_ffi.so \
  --json /tmp/fkv-compare.json
```

اعداد برای ماتریس صفحه اصلی فقط می توانند از یک اجرای قابل ردیابی بدست آیند:

```bash
python3 scripts/perf/fkv_compare_to_js.py \
  --json /tmp/fkv-compare.json --perf-js web/src/conf/perf.js \
  --machine "..." --source "CI run <id>"
```

`perf.yml` GitHub Actions دقیقاً این کار را انجام می دهد (نصب `librocksdb-dev`، آداپتورهای برنامه، اجرا
ماتریس ردیف 25 میلیونی، مصنوع را آپلود کنید و وقتی `backfill=true` صفحه را مستقیماً پر کنید.

### کالیبر

- **نسبت داده/کش**: 25,000,000 ردیف × 116 B ≈ 2766 مگابایت داده، 256 مگابایت حافظه نهان در هر موتور،
  ≈ 11:1، همراستا با بررسی رسمی RocksDB از 97 گیگابایت داده/6 گیگابایت حافظه پنهان (≈ 16:1).
- ** مقدار یکسان کش **: کش صفحه fkv (همان استخر شاخص/داده)، بلاک کش RocksDB
  (`cache_index_and_filter_blocks=true`، اندازه بلوک 4 کیلوبایت)، حافظه پنهان بلوک خود fjall
  بودجه ها همه به همان تعداد بایت تنظیم شده اند.
- ** کالیبر پایداری (ستون مقایسه از پیکربندی پیش فرض RocksDB، بدون تراز استفاده می کند)**: fkv 1×صفحه داده + هر دسته
  1×مانیفست `fdatasync` (ایزومورف به SyncData + AppendManifest از C++ EloqStore،
  هیچکدام سوئیچ خاموش ندارند)؛ ستون RocksDB از **پیکربندی پیش فرض** استفاده می کند (WAL روشن، `WriteOptions.sync=false`،
  بدون fsync متوالی)، fjall همچنین از پیش فرض (`PersistMode::Buffer`) استفاده می کند. بنابراین مرحله نوشتن (تک نوشتن /
  تفاوت بین نوشتن دسته ای) **تفاوت قدرت پایداری** است نه تفاوت پیاده سازی که باید در صفحه همراه با عدد ذکر شود.
  اگر می‌خواهید «چه کسی با همان قدرت همگام‌سازی سریع‌تر است» را تجزیه و تحلیل کنید، `--align-fsync` را اضافه کنید (RocksDB را با sync=true باز کنید،
  fjall از SyncAll استفاده می کند)، این گزینه برای ماتریس های منتشر شده خارجی استفاده نمی شود.
- **دو درایور fkv**: `--fkv-driver store` (پیش‌فرض، مستقیماً به یک `Store` در فرآیند متصل است، و
  RocksDB / fjall همچنین فراخوان های کتابخانه ای هستند) و `--fkv-driver runtime` (حالت استقرار: یک فرآیند
  `--fkv-shards` رشته‌های خرد، درخواست‌ها با کلید هدایت می‌شوند، با خواندن و نوشتن عمومی C++ EloqStore تراز می‌شوند.
  رابط). هر درخواست دومی باید از طریق صف + بیدار شدن بین رشته‌ای، بومی (macOS، IO فایل از طریق Thread Pool عبور می‌کند)
  زمان خواندن حدود 20 µs/زمان است که مرتبه‌ای کندتر از اتصال مستقیم در فرآیند است. در Linux/io_uring بسیار ارزان تر است، اما
  هنوز یک پرش ماتریس صفحه از کالیبر فروشگاه استفاده می‌کند و کالیبر زمان اجرا برای فرم استقرار در مقابل C++ استفاده می‌شود.
  مقایسه "واسط عمومی" (خوانش تک رشته ای زمان اجرا fkv حدود 50 کوپ در ثانیه است، C++ EloqStore FFI تک رشته ای
  خرده حدود 21 کپس در ثانیه).
- **کالیبر همزمانی خواندن**: شماره رشته کناری fkv = `min(readers, --read-max-concurrency)`، پیش‌فرض
  حد بالایی 4 است (هم تراز با vCPU ماشین ارزیابی)، **نه ** "یک رشته برای هر خواننده" - سطح بیش از حد فقط صف را افزایش می دهد.
  حافظه پنهان در هر رشته = 256 مگابایت / تعداد رشته ها (مقدار کل ثابت است، با خواننده ها خرد نمی شود) و استفاده می شود
  `FuturesUnordered` درخواست‌های `--read-window` (پیش‌فرض 16) را در جریان نگه دارید. سمت RocksDB است
  `readers` هر `std::thread` به طور همزمان خوانده می شود. حلقه تک رشته ای در سمت fjall (با نادیده گرفتن چرخ دنده خواننده،
  فقط به عنوان ستون مرجع). `--no-fkv-read-threads` می تواند به "N زنجیره ناهمزمان در هم تنیده در یک زمان اجرا منفرد" تبدیل شود.
  این عمق خط لوله است، نه همزمانی، و در بین موتورها قابل مقایسه نیست.
- **len()**: هیچ یک از سه موتور رابط شمارش O(1) ندارند. این خط نرخ شمارش جدول کامل است، نه جستجوی O(1).
