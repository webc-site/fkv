# Производительность

`fkv_bench` Тестовые нагрузки на запись, чтение и сканирование в фиксированном пространстве ключей.

```bash
cargo run --release -p fkv_bench -- \
  --workload write-read --rows 20000 --batch-size 100
```

Индикаторы включают пропускную способность, задержку на каждом этапе и пиковый RSS. выпуск рабочего процесса выпуска x86_64 /
`fkv_bench` двоичный файл для aarch64.

## Трехсторонний матч с RocksDB/fjall

`crate/perf/fkv_compare` Используйте тот же драйвер этапа и ту же кодировку ключа (8-байтовый индекс с обратным порядком байтов в конце,
Порядок словарей соответствует порядку индексов) Тест fkv, RocksDB, fjall: RocksDB пройден
`crate/perf/fkv_compare/cpp/rocksdb_ffi.cpp` Скомпилированная общая библиотека загружается с помощью dlopen (тот же C
ABI, сборка Rust не связана с RocksDB), fjall использует `fjall 3` напрямую. Каждый из трёх движков открывает библиотеку.
Продолжайте работать с той же библиотекой в ​​порядке этапов: массовая загрузка создает данные, а затем len/чтение точек/чтение диапазона/
Все удаления влияют на одни и те же данные.

```bash
cargo build --release -p fkv_compare
bash scripts/perf/build_rocksdb_ffi.sh # Пропустить третий столбец, если RocksDB отсутствует
./target/release/fkv_compare \
  --rows 25000000 --bulk-rows 25000000 --cache-bytes 268435456 \
  --readers 1,4,8,16,32 --workdir /tmp/fkv-compare \
  --rocksdb-lib target/perf/librocksdb_bench_ffi.so \
  --json /tmp/fkv-compare.json
```

Числа для матрицы домашней страницы могут быть получены только из одного отслеживаемого прогона:

```bash
python3 scripts/perf/fkv_compare_to_js.py \
  --json /tmp/fkv-compare.json --perf-js web/src/conf/perf.js \
  --machine "..." --source "Запуск CI <id>"
```

`perf.yml` GitHub Actions делает именно это (установите `librocksdb-dev`, программные адаптеры, запустите
Матрица строк размером 25 млн, загрузка артефакта и непосредственное заполнение страницы при `backfill=true`).

### калибр

- **Соотношение данных/кэша**: 25 000 000 строк × 116 Б ≈ 2766 МБ данных, 256 МБ кэша на механизм,
  ≈ 11:1, что соответствует официальному обзору RocksDB по 97 ГиБ данных и 6 ГиБ кэша (≈ 16:1).
- **Один и тот же объём кеша**: страничный кеш fkv (один и тот же пул индексов/данных), блочный кеш RocksDB.
  (`cache_index_and_filter_blocks=true`, размер блока 4 КиБ), собственный кеш блоков fjall
  Все бюджеты установлены на одинаковое количество байтов.
- **Калибр персистентности (столбец сравнения использует конфигурацию RocksDB по умолчанию, без выравнивания)**: fkv 1×страница данных + на пакет
  1×manifest `fdatasync` (изоморфен SyncData + AppendManifest C++ EloqStore,
  Ни у одного из них нет выключателя); в столбце RocksDB используется **конфигурация по умолчанию** (WAL включен, `WriteOptions.sync=false`,
  Нет последовательной fsync), fjall также использует значение по умолчанию (`PersistMode::Buffer`). Поэтому фаза записи (одиночная запись/
  Разница между пакетной записью) — это **разница в стойкости**, а не разница в реализации, которая должна быть указана на странице вместе с номером.
  Если вы хотите проанализировать, «кто быстрее при одинаковой силе синхронизации», добавьте `--align-fsync` (откройте RocksDB с sync=true,
  fjall использует SyncAll), эта опция не используется для матриц, публикуемых извне.
- **Два драйвера fkv**: `--fkv-driver store` (по умолчанию, напрямую подключены к одному `Store` внутри процесса и
  RocksDB/fjall также являются вызовами библиотеки) и `--fkv-driver runtime` (режим развертывания: процесс
  `--fkv-shards` потоки сегментов, запросы маршрутизируются по ключу, согласованы с общедоступным чтением и записью C++ EloqStore
  интерфейс). Каждый запрос последнего должен пройти через очередь + межпоточное пробуждение, нативное (macOS, файловый ввод-вывод проходит через пул потоков)
  Время чтения составляет около 20 мкс/время, что на порядок медленнее, чем прямое соединение в процессе; намного дешевле на Linux/io_uring, но
  Все равно прыжок. Матрица страниц использует калибр хранилища, а калибр времени выполнения используется для «формы развертывания против C++».
  Сравнение «Открытого интерфейса» (однопоточное чтение во время выполнения fkv составляет около 50 копий в секунду, однопоточное чтение C++ EloqStore FFI
  шард около 21 коп/с).
- **Чтение калибра параллелизма**: номер бокового потока fkv = `min(readers, --read-max-concurrency)`, по умолчанию
  Верхний предел — 4 (согласован с виртуальным ЦП оценочной машины), **а не** «один поток на считыватель» — превышение уровня только увеличивает очередь;
  Кэш на поток = 256 МБ / количество потоков (общий объем фиксирован, не измельчается с помощью читателей) и используется
  `FuturesUnordered` Оперативно сохраняйте запросы `--read-window` (по умолчанию 16). Сторона RocksDB
  `readers` Каждый `std::thread` считывается одновременно; однопоточный цикл на стороне fjall (игнорируя механизм считывателя,
  Только в качестве справочной колонки). `--no-fkv-read-threads` может вернуться к «чередующимся N асинхронным цепочкам в одной среде выполнения».
  Это глубина конвейера, а не параллелизма, и ее нельзя сравнивать между движками.
- **len()**: ни один из трех движков не имеет интерфейсов подсчета O(1). Эта строка представляет собой полную скорость счета таблицы, а не поиск O(1).
