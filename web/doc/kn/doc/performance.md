# ಕಾರ್ಯಕ್ಷಮತೆ

`fkv_bench` ಸ್ಥಿರ ಕೀಲಿ ಜಾಗದಲ್ಲಿ ಲೋಡ್‌ಗಳನ್ನು ಪರೀಕ್ಷಿಸಿ ಬರೆಯಿರಿ, ಓದಿರಿ ಮತ್ತು ಸ್ಕ್ಯಾನ್ ಮಾಡಿ.

```bash
cargo run --release -p fkv_bench -- \
  --workload write-read --rows 20000 --batch-size 100
```

ಸೂಚಕಗಳು ಥ್ರೋಪುಟ್, ಪ್ರತಿ ಹಂತದಲ್ಲಿ ಸುಪ್ತತೆ ಮತ್ತು ಗರಿಷ್ಠ RSS ಅನ್ನು ಒಳಗೊಂಡಿವೆ. ಬಿಡುಗಡೆ ವರ್ಕ್‌ಫ್ಲೋ ಬಿಡುಗಡೆ x86_64 /
aarch64 ಗಾಗಿ `fkv_bench` ಬೈನರಿ.

## RocksDB/fjall ನೊಂದಿಗೆ ಮೂರು-ಮಾರ್ಗದ ಹೊಂದಾಣಿಕೆ

`crate/perf/fkv_compare` ಅದೇ ಹಂತದ ಚಾಲಕ ಮತ್ತು ಅದೇ ಕೀ ಎನ್‌ಕೋಡಿಂಗ್ ಅನ್ನು ಬಳಸಿ (ಕೊನೆಯಲ್ಲಿ 8-ಬೈಟ್ ದೊಡ್ಡ-ಎಂಡಿಯನ್ ಸಬ್‌ಸ್ಕ್ರಿಪ್ಟ್,
ನಿಘಂಟಿನ ಕ್ರಮವು ಸಬ್‌ಸ್ಕ್ರಿಪ್ಟ್ ಕ್ರಮದೊಂದಿಗೆ ಸ್ಥಿರವಾಗಿದೆ) ಟೆಸ್ಟ್ fkv, RocksDB, fjall: RocksDB ಪಾಸ್
`crate/perf/fkv_compare/cpp/rocksdb_ffi.cpp` ಕಂಪೈಲ್ ಮಾಡಿದ ಹಂಚಿದ ಲೈಬ್ರರಿಯನ್ನು dlopen (ಅದೇ C) ನೊಂದಿಗೆ ಲೋಡ್ ಮಾಡಲಾಗಿದೆ
ABI, ರಸ್ಟ್ ಬಿಲ್ಡ್ RocksDB ಗೆ ಲಿಂಕ್ ಮಾಡುವುದಿಲ್ಲ), fjall ನೇರವಾಗಿ `fjall 3` ಅನ್ನು ಬಳಸುತ್ತದೆ. ಮೂರು ಎಂಜಿನ್‌ಗಳಲ್ಲಿ ಪ್ರತಿಯೊಂದೂ ಗ್ರಂಥಾಲಯವನ್ನು ತೆರೆಯುತ್ತದೆ.
ಹಂತಗಳ ಕ್ರಮದಲ್ಲಿ ಅದೇ ಲೈಬ್ರರಿಯಲ್ಲಿ ಮುನ್ನಡೆ: ಬೃಹತ್ ಲೋಡ್ ಡೇಟಾವನ್ನು ರಚಿಸುತ್ತದೆ, ಮತ್ತು ನಂತರ ಲೆನ್ / ಪಾಯಿಂಟ್ ಓದುವಿಕೆ / ಶ್ರೇಣಿಯ ಓದುವಿಕೆ /
ಅಳಿಸುವಿಕೆಗಳು ಒಂದೇ ಡೇಟಾವನ್ನು ಪರಿಣಾಮ ಬೀರುತ್ತವೆ.

```bash
cargo build --release -p fkv_compare
bash scripts/perf/build_rocksdb_ffi.sh # RocksDB ಇಲ್ಲದಿದ್ದರೆ ಮೂರನೇ ಕಾಲಮ್ ಅನ್ನು ಬಿಟ್ಟುಬಿಡಿ
./target/release/fkv_compare \
  --rows 25000000 --bulk-rows 25000000 --cache-bytes 268435456 \
  --readers 1,4,8,16,32 --workdir /tmp/fkv-compare \
  --rocksdb-lib target/perf/librocksdb_bench_ffi.so \
  --json /tmp/fkv-compare.json
```

ಮುಖಪುಟ ಮ್ಯಾಟ್ರಿಕ್ಸ್‌ನ ಸಂಖ್ಯೆಗಳು ಒಂದು ಪತ್ತೆಹಚ್ಚಬಹುದಾದ ರನ್‌ನಿಂದ ಮಾತ್ರ ಬರಬಹುದು:

```bash
python3 scripts/perf/fkv_compare_to_js.py \
  --json /tmp/fkv-compare.json --perf-js web/src/conf/perf.js \
  --machine "..." --source "CI ರನ್ <id>"
```

GitHub ಕ್ರಿಯೆಗಳ `perf.yml` ನಿಖರವಾಗಿ ಇದನ್ನು ಮಾಡುತ್ತದೆ (`librocksdb-dev`, ಪ್ರೋಗ್ರಾಂ ಅಡಾಪ್ಟರ್‌ಗಳನ್ನು ಸ್ಥಾಪಿಸಿ, ರನ್ ಮಾಡಿ
25M ಸಾಲು ಮ್ಯಾಟ್ರಿಕ್ಸ್, ಕಲಾಕೃತಿಯನ್ನು ಅಪ್‌ಲೋಡ್ ಮಾಡಿ ಮತ್ತು `backfill=true` ಮಾಡಿದಾಗ ನೇರವಾಗಿ ಪುಟವನ್ನು ಬ್ಯಾಕ್‌ಫಿಲ್ ಮಾಡಿ).

### ಕ್ಯಾಲಿಬರ್

- **ಡೇಟಾ/ಸಂಗ್ರಹ ಅನುಪಾತ**: 25,000,000 ಸಾಲುಗಳು × 116 B ≈ 2766 MiB ಡೇಟಾ, ಪ್ರತಿ ಎಂಜಿನ್‌ಗೆ 256 MiB ಸಂಗ್ರಹ,
  ≈ 11:1, 97 GiB ಡೇಟಾ/6 GiB ಸಂಗ್ರಹದ (≈ 16:1) ರಾಕ್ಸ್‌ಡಿಬಿಯ ಅಧಿಕೃತ ವಿಮರ್ಶೆಯೊಂದಿಗೆ ಜೋಡಿಸಲಾಗಿದೆ.
- **ಅದೇ ಪ್ರಮಾಣದ ಸಂಗ್ರಹ**: fkv ನ ಪುಟ ಸಂಗ್ರಹ (ಸೂಚ್ಯಂಕ/ಡೇಟಾ ಅದೇ ಪೂಲ್), RocksDB ಯ ಬ್ಲಾಕ್ ಸಂಗ್ರಹ
  (`cache_index_and_filter_blocks=true`, ಬ್ಲಾಕ್ ಗಾತ್ರ 4 KiB), fjall ನ ಸ್ವಂತ ಬ್ಲಾಕ್ ಸಂಗ್ರಹ
  ಬಜೆಟ್‌ಗಳನ್ನು ಒಂದೇ ಸಂಖ್ಯೆಯ ಬೈಟ್‌ಗಳಿಗೆ ಹೊಂದಿಸಲಾಗಿದೆ.
- **ಪರ್ಸಿಸ್ಟೆನ್ಸ್ ಕ್ಯಾಲಿಬರ್ (ಹೋಲಿಕೆ ಕಾಲಮ್ ರಾಕ್ಸ್‌ಡಿಬಿ ಡೀಫಾಲ್ಟ್ ಕಾನ್ಫಿಗರೇಶನ್ ಅನ್ನು ಜೋಡಣೆ ಇಲ್ಲದೆ ಬಳಸುತ್ತದೆ)**: fkv 1×ಡೇಟಾ ಪುಟ + ಪ್ರತಿ ಬ್ಯಾಚ್
  1× ಮ್ಯಾನಿಫೆಸ್ಟ್ `fdatasync` (ಐಸೊಮಾರ್ಫಿಕ್ ಟು ಸಿಂಕ್ಡೇಟಾ + AppendManifest of C++ EloqStore,
  ಎರಡೂ ಆಫ್ ಸ್ವಿಚ್ ಹೊಂದಿಲ್ಲ); RocksDB ಕಾಲಮ್ **ಡೀಫಾಲ್ಟ್ ಕಾನ್ಫಿಗರೇಶನ್** ಅನ್ನು ಬಳಸುತ್ತದೆ (WAL ಆನ್, `WriteOptions.sync=false`,
  ಅನುಕ್ರಮ fsync ಇಲ್ಲ), fjall ಡೀಫಾಲ್ಟ್ ಅನ್ನು ಸಹ ಬಳಸುತ್ತದೆ (`PersistMode::Buffer`). ಆದ್ದರಿಂದ ಬರೆಯುವ ಹಂತ (ಏಕ ಬರಹ /
  ಬ್ಯಾಚ್ ಬರಹಗಳ ನಡುವಿನ ವ್ಯತ್ಯಾಸ) **ಪರ್ಸಿಸ್ಟೆನ್ಸ್ ಸ್ಟ್ರೆಂಥ್ ಡಿಫರೆನ್ಸ್**, ಅನುಷ್ಠಾನ ವ್ಯತ್ಯಾಸವಲ್ಲ, ಇದನ್ನು ಸಂಖ್ಯೆಯ ಜೊತೆಗೆ ಪುಟದಲ್ಲಿ ನಮೂದಿಸಬೇಕು.
  ನೀವು "ಅದೇ ಸಿಂಕ್ರೊನೈಸೇಶನ್ ಸಾಮರ್ಥ್ಯದ ಅಡಿಯಲ್ಲಿ ಯಾರು ವೇಗವಾಗಿದ್ದಾರೆ" ಎಂದು ವಿಶ್ಲೇಷಿಸಲು ಬಯಸಿದರೆ, `--align-fsync` ಸೇರಿಸಿ (Sync=true ಜೊತೆಗೆ RocksDB ತೆರೆಯಿರಿ,
  fjall SyncAll ಅನ್ನು ಬಳಸುತ್ತದೆ), ಈ ಆಯ್ಕೆಯನ್ನು ಬಾಹ್ಯವಾಗಿ ಪ್ರಕಟವಾದ ಮ್ಯಾಟ್ರಿಕ್ಸ್‌ಗಳಿಗೆ ಬಳಸಲಾಗುವುದಿಲ್ಲ.
- **ಎರಡು fkv ಡ್ರೈವರ್‌ಗಳು**: `--fkv-driver store` (ಡೀಫಾಲ್ಟ್, ಪ್ರಕ್ರಿಯೆಯೊಳಗೆ ನೇರವಾಗಿ ಒಂದೇ `Store` ಗೆ ಸಂಪರ್ಕಿಸಲಾಗಿದೆ, ಮತ್ತು
  RocksDB / fjall ಕೂಡ ಲೈಬ್ರರಿ ಕರೆಗಳು) ಮತ್ತು `--fkv-driver runtime` (ನಿಯೋಜನೆ ಮೋಡ್: ಒಂದು ಪ್ರಕ್ರಿಯೆ
  `--fkv-shards` ಚೂರು ಥ್ರೆಡ್‌ಗಳು, ವಿನಂತಿಗಳನ್ನು ಕೀ ಮೂಲಕ ರೂಟ್ ಮಾಡಲಾಗುತ್ತದೆ, C++ EloqStore ನ ಸಾರ್ವಜನಿಕ ಓದುವಿಕೆ ಮತ್ತು ಬರವಣಿಗೆಯೊಂದಿಗೆ ಜೋಡಿಸಲಾಗಿದೆ
  ಇಂಟರ್ಫೇಸ್). ನಂತರದ ಪ್ರತಿಯೊಂದು ವಿನಂತಿಯು ಕ್ಯೂ + ಕ್ರಾಸ್-ಥ್ರೆಡ್ ವೇಕ್-ಅಪ್, ಸ್ಥಳೀಯ (macOS, ಫೈಲ್ IO ಥ್ರೆಡ್ ಪೂಲ್ ಮೂಲಕ ಹೋಗುತ್ತದೆ) ಮೂಲಕ ಹೋಗಬೇಕಾಗುತ್ತದೆ.
  ಓದುವ ಸಮಯವು ಸುಮಾರು 20 µs/ಸಮಯವಾಗಿದೆ, ಇದು ಪ್ರಕ್ರಿಯೆಯಲ್ಲಿ ನೇರ ಸಂಪರ್ಕಕ್ಕಿಂತ ನಿಧಾನವಾದ ಕ್ರಮವಾಗಿದೆ; Linux/io_uring ನಲ್ಲಿ ಹೆಚ್ಚು ಅಗ್ಗ, ಆದರೆ
  ಇನ್ನೂ ಒಂದು ಜಿಗಿತ. ಪುಟ ಮ್ಯಾಟ್ರಿಕ್ಸ್ ಸ್ಟೋರ್ ಕ್ಯಾಲಿಬರ್ ಅನ್ನು ಬಳಸುತ್ತದೆ ಮತ್ತು ರನ್ಟೈಮ್ ಕ್ಯಾಲಿಬರ್ ಅನ್ನು "ನಿಯೋಜನೆ ಫಾರ್ಮ್ ವಿರುದ್ಧ C++ ಗಾಗಿ ಬಳಸಲಾಗುತ್ತದೆ
  "ಸಾರ್ವಜನಿಕ ಇಂಟರ್ಫೇಸ್" ನ ಹೋಲಿಕೆ (fkv ರನ್ಟೈಮ್ ಸಿಂಗಲ್-ಥ್ರೆಡ್ ರೀಡಿಂಗ್ ಸುಮಾರು 50 kops/s, C++ EloqStore FFI ಸಿಂಗಲ್-ಥ್ರೆಡ್
  ಚೂರು ಸುಮಾರು 21 ಕಾಪ್ಸ್/ಸೆ).
- **ಕರೆನ್ಸಿ ಕ್ಯಾಲಿಬರ್ ಅನ್ನು ಓದಿ**: fkv ಸೈಡ್ ಥ್ರೆಡ್ ಸಂಖ್ಯೆ = `min(readers, --read-max-concurrency)`, ಡೀಫಾಲ್ಟ್
  ಮೇಲಿನ ಮಿತಿಯು 4 ಆಗಿದೆ (ಮೌಲ್ಯಮಾಪನ ಯಂತ್ರ vCPU ನೊಂದಿಗೆ ಜೋಡಿಸಲಾಗಿದೆ), ** ಅಲ್ಲ ** "ಪ್ರತಿ ರೀಡರ್‌ಗೆ ಒಂದು ಥ್ರೆಡ್" - ಮೀರಿದ ಮಟ್ಟವು ಸರದಿಯನ್ನು ಹೆಚ್ಚಿಸುತ್ತದೆ;
  ಪ್ರತಿ ಥ್ರೆಡ್‌ಗೆ ಸಂಗ್ರಹ = 256 MiB / ಥ್ರೆಡ್‌ಗಳ ಸಂಖ್ಯೆ (ಒಟ್ಟು ಮೊತ್ತವನ್ನು ನಿಗದಿಪಡಿಸಲಾಗಿದೆ, ಓದುಗರೊಂದಿಗೆ ಚೂರುಚೂರು ಮಾಡಲಾಗಿಲ್ಲ), ಮತ್ತು ಬಳಸಲಾಗುತ್ತದೆ
  `FuturesUnordered` `--read-window` (ಡೀಫಾಲ್ಟ್ 16) ವಿನಂತಿಗಳನ್ನು ಫ್ಲೈನಲ್ಲಿ ಇರಿಸಿಕೊಳ್ಳಿ. RocksDB ಸೈಡ್ ಆಗಿದೆ
  `readers` ಪ್ರತಿ `std::thread` ಏಕಕಾಲದಲ್ಲಿ ಓದುತ್ತದೆ; fjall ಬದಿಯಲ್ಲಿ ಏಕ-ಥ್ರೆಡ್ ಲೂಪ್ (ರೀಡರ್ಸ್ ಗೇರ್ ಅನ್ನು ನಿರ್ಲಕ್ಷಿಸುವುದು,
  ಉಲ್ಲೇಖ ಕಾಲಮ್ ಆಗಿ ಮಾತ್ರ). `--no-fkv-read-threads` "ಒಂದೇ ರನ್‌ಟೈಮ್‌ನಲ್ಲಿ ಇಂಟರ್‌ಲೀವ್ಡ್ N ಅಸಮಕಾಲಿಕ ಸರಪಳಿಗಳಿಗೆ" ಹಿಂತಿರುಗಬಹುದು.
  ಅದು ಪೈಪ್‌ಲೈನ್ ಆಳವಾಗಿದೆ, ಏಕಕಾಲಿಕವಲ್ಲ ಮತ್ತು ಎಂಜಿನ್‌ಗಳಾದ್ಯಂತ ಹೋಲಿಸಲಾಗುವುದಿಲ್ಲ.
- **len()**: ಮೂರು ಎಂಜಿನ್‌ಗಳಲ್ಲಿ ಯಾವುದೂ O(1) ಎಣಿಸುವ ಇಂಟರ್‌ಫೇಸ್‌ಗಳನ್ನು ಹೊಂದಿಲ್ಲ. ಈ ಸಾಲು ಪೂರ್ಣ ಟೇಬಲ್ ಎಣಿಕೆಯ ದರವಾಗಿದೆ, O(1) ಲುಕಪ್ ಅಲ್ಲ.
