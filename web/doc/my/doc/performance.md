Dictionary order သည် subscript order နှင့် ကိုက်ညီသည်) Test fkv, RocksDB, fjall: RocksDB အောင်သွားသည်
`crate/perf/fkv_compare/cpp/rocksdb_ffi.cpp`စုစည်းထားသော မျှဝေထားသောစာကြည့်တိုက်ကို dlopen (တူညီသော C
ABI၊ Rust build သည် RocksDB နှင့် ချိတ်ဆက်ခြင်းမရှိပါ) fjall သည် `fjall 3` တိုက်ရိုက်အသုံးပြုသည်။ အင်ဂျင်သုံးလုံးမှ တစ်ခုစီသည် စာကြည့်တိုက်တစ်ခုဖွင့်သည်။
အဆင့်များအစီအစဥ်အတိုင်း တူညီသောဒစ်ဂျစ်တိုက်တွင် ရှေ့တိုးသည်- အစုလိုက်ဝန်သည် ဒေတာကိုဖန်တီးသည်၊ ထို့နောက် len / point reading / range reading /
ဖျက်လိုက်မှုအားလုံးသည် တူညီသောဒေတာကို သက်ရောက်မှုရှိသည်။

```bash
cargo build --release -p fkv_compare
bash scripts/perf/build_rocksdb_ffi.sh # RocksDB မရှိပါက တတိယကော်လံကို ကျော်ပါ။

  --rows 25000000 --bulk-rows 25000000 --cache-bytes 268435456 \

  --json /tmp/fkv-compare.json
```

### လုပ်ရည်ကိုင်ရည်

- **Data/Cache Ratio**- 25,000,000 အတန်း × 116 B ≈ ဒေတာ 2766 MiB၊ အင်ဂျင်တစ်ခုလျှင် ကက်ရှ် 256 MiB၊
  ≈ 11:1၊ 97 GiB ဒေတာ/6 GiB cache (≈ 16:1) ကို RocksDB ၏တရားဝင်ပြန်လည်သုံးသပ်မှုနှင့်အညီ လိုက်လျောညီထွေဖြစ်စေသည်။
- **တူညီသော ကက်ရှ်ပမာဏ**- fkv ၏ စာမျက်နှာ ကက်ရှ် (အညွှန်းကိန်း/ဒေတာ တူညီသော ရေကန်)၊ RocksDB ၏ ဘလောက်ကက်ရှ်
  (`cache_index_and_filter_blocks=true`၊ ပိတ်ဆို့အရွယ်အစား 4 KiB)၊ fjall ၏ ကိုယ်ပိုင်ပိတ်ဆို့ ကက်ရှ်
  ဘတ်ဂျက်အားလုံးကို တူညီသော bytes အရေအတွက်အဖြစ် သတ်မှတ်ထားသည်။
- ** ခံနိုင်ရည်ရှိမှု အတိုင်းအတာ ( နှိုင်းယှဉ်ကော်လံသည် ချိန်ညှိခြင်းမရှိဘဲ RocksDB ၏ ပုံသေဖွဲ့စည်းပုံကို အသုံးပြုသည် )**- fkv 1 × ဒေတာစာမျက်နှာ + တစ်သုတ်
  1×manifest `fdatasync` (Isomorphic to SyncData + AppendManifest C++ EloqStore၊
  off switch လည်း မရှိပါ။ RocksDB ကော်လံသည် **မူလပုံစံဖွဲ့စည်းမှု** ကိုအသုံးပြုသည် (WAL on, `WriteOptions.sync=false`၊
  ဆင့်ကဲ fsync မရှိပါ၊ fjall သည် ပုံသေ (`PersistMode::Buffer`) ကို အသုံးပြုပါသည်။ ထို့ကြောင့် ရေးရန် အဆင့် ( single write / ၊
  အသုတ်ရေးခြင်းကြား ခြားနားချက်) သည် နံပါတ်နှင့်အတူ စာမျက်နှာပေါ်တွင် ဖော်ပြရမည့် အကောင်အထည်ဖော်မှု ကွာခြားချက်မဟုတ်ဘဲ ** စွဲမြဲခိုင်ခံ့မှု ကွာခြားချက်** ဖြစ်သည်။
  "တူညီသော synchronization strength အောက်တွင် ဘယ်သူမြန်သနည်း" ကိုခွဲခြမ်းစိတ်ဖြာလိုပါက `--align-fsync` (Sync=true ဖြင့် RocksDB ကိုဖွင့်ပါ၊
  fjall သည် SyncAll ကိုအသုံးပြုသည်)၊ ဤရွေးချယ်မှုကို ပြင်ပမှထုတ်ဝေသော matrices အတွက် အသုံးမပြုပါ။
- **fkv ဒရိုက်ဘာ နှစ်ခု**: `--fkv-driver store` (မူလ၊ လုပ်ငန်းစဉ်အတွင်း `Store` တစ်ခုတည်းသို့ တိုက်ရိုက်ချိတ်ဆက်ထားပြီး၊
  RocksDB / fjall များသည် စာကြည့်တိုက်ခေါ်ဆိုမှုများလည်းဖြစ်သည်) နှင့် `--fkv-driver runtime` (အသုံးချမုဒ်- လုပ်ငန်းစဉ်တစ်ခု
  `--fkv-shards` ကြမ်းတမ်းသော စာတွဲများ၊ တောင်းဆိုမှုများကို သော့ဖြင့် ဖြတ်သန်းသည်၊ C++ EloqStore ၏ အများသူငှာဖတ်ရှုခြင်းနှင့် ရေးသားခြင်းတို့ဖြင့် ချိန်ညှိထားသည်။
  အင်တာဖေ့စ်)။ နောက်ဆုံးတောင်းဆိုချက်တစ်ခုစီသည် တန်းစီခြင်း + ကြိုးတန်းနိုးထခြင်း၊ မူရင်း (macOS၊ ဖိုင် IO သည် thread pool မှတဆင့်သွားသည်)၊
  စာဖတ်ချိန်သည် 20 µs/time ခန့်ဖြစ်ပြီး၊ ၎င်းသည် လုပ်ငန်းစဉ်အတွင်း တိုက်ရိုက်ချိတ်ဆက်မှုထက် ပြင်းအားနှေးကွေးသော အစီအစဥ်တစ်ခုဖြစ်သည်။ Linux/io_uring တွင် များစွာစျေးသက်သာသော်လည်း၊
  ခုန်နေတုန်း။ စာမျက်နှာ matrix သည် store caliber ကိုအသုံးပြုပြီး runtime caliber ကို "deployment form vs C++ အတွက်အသုံးပြုသည်
  "Public Interface" ကို နှိုင်းယှဉ်ခြင်း (fkv runtime single-thread reading သည် 50 kops/s ခန့်၊ C++ EloqStore FFI single-thread
  21 kops/s ခန့်)။
- ** တူညီသောငွေကြေးပမာဏကိုဖတ်ရန်**: fkv ဘေးထွက်ချည်နံပါတ် = `min(readers, --read-max-concurrency)`၊ မူရင်း
  အပေါ်ပိုင်းကန့်သတ်ချက်မှာ 4 (အကဲဖြတ်စက် vCPU နှင့် ချိန်ညှိထားသည်) **မဟုတ်ပါ** "စာဖတ်သူအတွက် စာတွဲတစ်ခု" - ကျော်လွန်သောအဆင့်သည် တန်းစီခြင်းကိုသာ တိုးစေသည်။
  စာတွဲတစ်ခုလျှင် ကက်ရှ် = 256 MiB / စာတွဲအရေအတွက် (စုစုပေါင်းပမာဏကို ပုံသေသတ်မှတ်ထားပြီး၊ စာဖတ်သူများနှင့် ဖျက်စီးခြင်းမပြုပါ) နှင့် အသုံးပြုသည်
  `FuturesUnordered` `--read-window` (မူလ 16) တောင်းဆိုချက်များကို အမြန်သိမ်းဆည်းပါ။ RocksDB ဘက်ကပါ။
  `readers`တစ်ခုစီ `std::thread` တစ်ပြိုင်နက် ဖတ်သည်၊ fjall ဘက်ခြမ်းရှိ single-threaded loop (စာဖတ်သူဂီယာကိုလျစ်လျူရှုခြင်း၊
  ကိုးကားကော်လံအဖြစ်သာ)။ `--no-fkv-read-threads` runtime တစ်ခုတည်းတွင် "ကြားဖြတ်ထားသော N asynchronous chains" သို့ ပြန်သွားနိုင်သည်။
  ၎င်းသည် ပိုက်လိုင်းအတိမ်အနက်၊ ဆက်စပ်မှုမဟုတ်ဘဲ၊ အင်ဂျင်များနှင့် နှိုင်းယှဉ်၍မရပါ။
