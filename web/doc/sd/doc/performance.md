# ڪارڪردگي

`fkv_bench` ٽيسٽ لکو، پڙهو، ۽ اسڪين لوڊ ڪريو مقرر ڪيل ڪي اسپيس تي.

```bash
cargo run --release -p fkv_bench -- \
  --workload write-read --rows 20000 --batch-size 100
```

اشارن ۾ شامل آهن throughput، هر اسٽيج تي ويڪرائي، ۽ چوٽي RSS. ڪم فلو ڇڏڻ x86_64 /
`fkv_bench` بائنري aarch64 لاءِ.

## RocksDB/fjall سان ٽي طرفي ميلاپ

`crate/perf/fkv_compare` ساڳيو اسٽيج ڊرائيور ۽ ساڳي ڪيئي انڪوڊنگ استعمال ڪريو (آخر ۾ 8-بائيٽ وڏي-انڊين سبسڪرپشن،
ڊڪشنري آرڊر سبسڪرپٽ آرڊر سان مطابقت رکي ٿو) ٽيسٽ fkv، RocksDB، fjall: RocksDB منظور
`crate/perf/fkv_compare/cpp/rocksdb_ffi.cpp` مرتب ڪيل شيئر لائبريري ڊيلوپن سان ڀريل آهي (ساڳي سي
ABI، Rust build RocksDB سان ڳنڍيل نه آهي)، fjall استعمال ڪري ٿو `fjall 3` سڌو. ٽن انجڻين مان هر هڪ لائبريري کوليندو آهي.
مرحلن جي ترتيب ۾ ساڳئي لائبريري تي اڳڀرائي: بلڪ لوڊ ڊيٽا ٺاهي ٿو، ۽ پوء لين / پوائنٽ پڙهڻ / رينج پڙهڻ /
حذف ڪرڻ وارا سڀئي ساڳيا ڊيٽا کي متاثر ڪن ٿا.

```bash
cargo build --release -p fkv_compare
bash scripts/perf/build_rocksdb_ffi.sh # ٽئين ڪالمن کي ڇڏي ڏيو جيڪڏھن ڪو RocksDB نه آھي
./target/release/fkv_compare \
  --rows 25000000 --bulk-rows 25000000 --cache-bytes 268435456 \
  --readers 1,4,8,16,32 --workdir /tmp/fkv-compare \
  --rocksdb-lib target/perf/librocksdb_bench_ffi.so \
  --json /tmp/fkv-compare.json
```

هوم پيج ميٽرڪس جا انگ صرف هڪ ٽريسيبل رن مان اچي سگهن ٿا:

```bash
python3 scripts/perf/fkv_compare_to_js.py \
  --json /tmp/fkv-compare.json --perf-js web/src/conf/perf.js \
  --machine "..." --source "CI run <id>"
```

GitHub ڪارناما '`perf.yml` بلڪل ائين ئي ڪري ٿو (انسٽال `librocksdb-dev`، پروگرام ايڊاپٽر، هلائي
25M قطار ميٽرڪس، آرٽيڪل اپ لوڊ ڪريو، ۽ سڌو صفحي کي واپس ڀريو جڏھن `backfill=true`).

### قابليت

- **ڊيٽا/ڪيش جو تناسب**: 25,000,000 قطارون × 116 B ≈ 2766 MiB ڊيٽا، 256 MiB ڪيش في انجڻ،
  ≈ 11:1، 97 GiB ڊيٽا/6 GiB ڪيش جي RocksDB جي سرڪاري جائزي سان ترتيب ڏنل (≈ 16:1).
- **ساڳئي مقدار جي ڪيش**: fkv جي پيج ڪيش (انڊيڪس/ڊيٽا ساڳي پول)، RocksDB جي بلاڪ ڪيش
  (`cache_index_and_filter_blocks=true`، بلاڪ سائيز 4 KiB)، fjall جي پنهنجي بلاڪ ڪيش
  بجيٽون سڀ هڪ ئي تعداد ۾ بائيٽ تي مقرر ٿيل آهن.
- ** پرسسٽنس ڪيليبر (مقابلي وارو ڪالم RocksDB ڊفالٽ ڪنفيگريشن استعمال ڪري ٿو، بغير ترتيب جي)**: fkv 1×data page + per batch
  1×منظور `fdatasync` (Isomorphic to SyncData + AppendManifest of C++ EloqStore،
  نه ته ڪو بند سوئچ آهي)؛ RocksDB ڪالم استعمال ڪري ٿو **ڊفالٽ ڪنفيگريشن** (WAL on, `WriteOptions.sync=false`،
  ڪابه ترتيب وار fsync نه آهي، fjall به ڊفالٽ استعمال ڪري ٿو (`PersistMode::Buffer`). تنهن ڪري لکڻ جو مرحلو (اڪيلو لکڻ /
  بيچ لکڻ جي وچ ۾ فرق) **مسلسل طاقت جو فرق** آهي، نه پر عمل درآمد جو فرق، جيڪو نمبر سان گڏ صفحي تي بيان ڪيو وڃي.
  جيڪڏھن توھان تجزيو ڪرڻ چاھيو ٿا "ڪير تيز آھي ساڳي هم وقت سازي جي طاقت تحت"، شامل ڪريو `--align-fsync` (open RocksDB with sync=true،
  fjall SyncAll استعمال ڪري ٿو)، هي اختيار خارجي طور تي شايع ٿيل ميٽرڪس لاءِ استعمال نه ڪيو ويو آهي.
- **ٻه fkv ڊرائيور**: `--fkv-driver store` (ڊفالٽ، سڌو سنئون هڪ واحد سان ڳنڍيل آهي `Store` عمل جي اندر، ۽
  RocksDB / fjall پڻ لائبريري ڪالون آهن) ۽ `--fkv-driver runtime` (تعميراتي موڊ: هڪ عمل
  `--fkv-shards` شارڊ ٿريڊز، درخواستون ڪن جي ذريعي روٽ ڪيون وينديون آهن، C++ EloqStore جي عوامي پڙهڻ ۽ لکڻ سان ترتيب ڏنل
  انٽرفيس). پوئين جي هر درخواست کي قطار ذريعي وڃڻ جي ضرورت آهي + ڪراس-ٿريڊ ويڪ اپ، اصلي (macOS، فائل IO ٿريڊ پول ذريعي وڃي ٿو)
  پڙهڻ جو وقت تقريباً 20 µs/وقت آهي، جيڪو عمل ۾ سڌي ڪنيڪشن جي ڀيٽ ۾ سست رفتاري جو حڪم آهي؛ Linux/io_uring تي تمام گهڻو سستو، پر
  اڃا هڪ جمپ. صفحو ميٽرڪس اسٽور ڪيليبر استعمال ڪري ٿو، ۽ رن ٽائم ڪليبر استعمال ڪيو ويندو آهي "تعميراتي فارم بمقابله C++"
  "عوامي انٽرفيس" جو مقابلو (fkv رن ٽائم سنگل ٿريڊ ريڊنگ اٽڪل 50 kops/s، C++ EloqStore FFI سنگل ٿريڊ
  شارڊ اٽڪل 21 ڪوپس/s).
- **پڙهو ڪنورنسي ڪيليبر**: fkv پاسي واري سلسلي جو نمبر = `min(readers, --read-max-concurrency)`، ڊفالٽ
  مٿين حد 4 آهي (تجزيي واري مشين vCPU سان ترتيب ڏنل)، ** نه** "هڪ ٿريڊ في ريڊر" - وڌايل سطح صرف قطار وڌائي ٿي؛
  ڪيش في ٿريڊ = 256 MiB / سلسلي جو تعداد (مجموعي رقم مقرر ٿيل آهي، پڙهندڙن سان ٽڪرا نه ڪيو ويو آهي)، ۽ استعمال ٿيل
  `FuturesUnordered` رکو `--read-window` (ڊفالٽ 16) درخواستون پرواز تي. RocksDB پاسي آهي
  `readers` هر هڪ `std::thread` هڪ ئي وقت پڙهندو آهي؛ fjall پاسي تي اڪيلو ڌاڳو وارو لوپ (ريڊر گيئر کي نظرانداز ڪرڻ،
  صرف هڪ حوالو ڪالم جي طور تي). `--no-fkv-read-threads` "interleaved N asynchronous chains on one runtime" ڏانهن واپس خراب ٿي سگھي ٿو.
  اھو پائپ لائن جي کوٽائي آھي، اتفاق سان نه، ۽ انجڻ جي وچ ۾ موازنہ نه آھي.
- **len()**: ٽنهي انجڻن مان ڪنهن ۾ به O(1) ڳڻپ انٽرفيس نه آهي. هي لڪير آهي مڪمل جدول جي ڳڻپ جي شرح، نه O(1) ڏسڻ.
