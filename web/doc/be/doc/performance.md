# Прадукцыйнасць

`fkv_bench` Тэставыя загрузкі запісу, чытання і сканавання ў фіксаванай прасторы ключоў.

```bash
cargo run --release -p fkv_bench -- \
  --workload write-read --rows 20000 --batch-size 100
```

Паказчыкі ўключаюць прапускную здольнасць, затрымку на кожным этапе і пік RSS. выпуск працоўнага працэсу выпуск x86_64 /
`fkv_bench` двайковы файл для aarch64.

## Трохбаковы матч з RocksDB/fjall

`crate/perf/fkv_compare` Выкарыстоўвайце той жа драйвер этапу і аднолькавае кадаванне ключоў (8-байтны індэкс з пачаткам байта ў канцы,
Парадак слоўнікаў адпавядае парадку індэксаў) Тэст fkv, RocksDB, fjall: RocksDB пройдзены
`crate/perf/fkv_compare/cpp/rocksdb_ffi.cpp` Скампіляваная агульная бібліятэка загружаецца з дапамогай dlopen (той жа C
ABI, зборка Rust не спасылаецца на RocksDB), fjall выкарыстоўвае `fjall 3` непасрэдна. Кожны з трох рухавікоў адкрывае бібліятэку.
Пераход да адной і той жа бібліятэцы ў парадку этапаў: масавая загрузка стварае даныя, а затым len / кропкавае чытанне / дыяпазон чытання /
Усе выдаленні ўплываюць на адны і тыя ж даныя.

```bash
cargo build --release -p fkv_compare
bash scripts/perf/build_rocksdb_ffi.sh # Прапусціць трэці слупок, калі няма RocksDB
./target/release/fkv_compare \
  --rows 25000000 --bulk-rows 25000000 --cache-bytes 268435456 \
  --readers 1,4,8,16,32 --workdir /tmp/fkv-compare \
  --rocksdb-lib target/perf/librocksdb_bench_ffi.so \
  --json /tmp/fkv-compare.json
```

Лічбы для матрыцы галоўнай старонкі могуць паходзіць толькі з аднаго адсочванага прагону:

```bash
python3 scripts/perf/fkv_compare_to_js.py \
  --json /tmp/fkv-compare.json --perf-js web/src/conf/perf.js \
  --machine "..." --source "CI run <id>"
```

`perf.yml` GitHub Actions робіць менавіта гэта (устаноўка `librocksdb-dev`, праграмныя адаптары, запуск
Матрыца радкоў 25M, запампаваць артэфакт і непасрэдна запоўніць старонку, калі `backfill=true`).

### калібр

- **Суадносіны даных/кэша**: 25 000 000 радкоў × 116 Б ≈ 2766 МіБ даных, 256 МіБ кэша на механізм,
  ≈ 11:1, у адпаведнасці з афіцыйным аглядам RocksDB 97 ГіБ даных/6 ГіБ кэша (≈ 16:1).
- **Аднолькавы аб'ём кэша**: кэш старонак fkv (той жа пул індэксаў/дадзеных), кэш блокаў RocksDB
  (`cache_index_and_filter_blocks=true`, памер блока 4 КіБ), уласны кэш блокаў fjall
  Усе бюджэты ўстаноўлены на аднолькавую колькасць байтаў.
- **Калібр устойлівасці (у слупку параўнання выкарыстоўваецца канфігурацыя RocksDB па змаўчанні, без выраўноўвання)**: fkv 1×старонка даных + за партыю
  1×маніфест `fdatasync` (ізаморфны SyncData + AppendManifest C++ EloqStore,
  Ні ў аднаго з іх няма выключальніка); слупок RocksDB выкарыстоўвае **канфігурацыю па змаўчанні** (WAL уключаны, `WriteOptions.sync=false`,
  Няма паслядоўнага fsync), fjall таксама выкарыстоўвае стандартнае (`PersistMode::Buffer`). Такім чынам, фаза запісу (аднаразовая запіс /
  Розніца паміж пакетнымі запісамі) заключаецца ў **розніцы трываласці**, а не ў рэалізацыі, якая павінна быць указана на старонцы разам з нумарам.
  Калі вы хочаце прааналізаваць, "хто хутчэй пры аднолькавай сіле сінхранізацыі", дадайце `--align-fsync` (адкрыйце RocksDB з sync=true,
  fjall выкарыстоўвае SyncAll), гэтая опцыя не выкарыстоўваецца для апублікаваных звонку матрыц.
- **Два драйверы fkv**: `--fkv-driver store` (па змаўчанні, непасрэдна падлучаны да аднаго `Store` у працэсе, і
  RocksDB / fjall таксама выклікаюць бібліятэкі) і `--fkv-driver runtime` (рэжым разгортвання: працэс
  `--fkv-shards` паток аскепкаў, запыты накіроўваюцца па ключы, у адпаведнасці з публічным чытаннем і запісам C++ EloqStore
  інтэрфейс). Кожны запыт апошняга павінен прайсці праз чаргу + міжпаточнае абуджэнне, уласны (macOS, файл IO праходзіць праз пул патокаў)
  Час чытання складае каля 20 мкс/час, што на парадак павольней, чым прамое злучэнне ў працэсе; значна танней на Linux/io_uring, але
  Яшчэ скачок. Матрыца старонкі выкарыстоўвае калібр крамы, а калібр часу выканання выкарыстоўваецца для "формы разгортвання супраць C++
  Параўнанне «Публічнага інтэрфейсу» (аднаструменнае чытанне падчас выканання fkv складае каля 50 коп/с, C++ EloqStore FFI аднаструменны
  асколак каля 21 кап/с).
- **Калібр паралелізму чытання**: нумар бакавой ніткі fkv = `min(readers, --read-max-concurrency)`, па змаўчанні
  Верхняя мяжа складае 4 (у адпаведнасці з vCPU ацэначнай машыны), **а не** «адзін паток на счытвальнік» — перавышаны ўзровень толькі павялічвае чаргу;
  Кэш на паток = 256 МіБ / колькасць патокаў (агульны аб'ём фіксаваны, не здрабняецца чытачамі) і выкарыстоўваецца
  `FuturesUnordered` Захоўваць `--read-window` (па змаўчанні 16) запыты на ляту. бок RocksDB ёсць
  `readers` Кожны `std::thread` чытае адначасова; аднаструменны цыкл на баку fjall (без уліку рыдэраў,
  Толькі як даведачны слупок). `--no-fkv-read-threads` можа вярнуцца да "перамежаваных N асінхронных ланцужкоў у адным асяроддзі выканання".
  Гэта глыбіня канвеера, а не паралелізм, і гэта не параўнальна паміж рухавікамі.
- **len()**: Ні адзін з трох рухавікоў не мае інтэрфейсаў падліку O(1). Гэты радок паказвае поўную хуткасць падліку табліцы, а не пошук O(1).
