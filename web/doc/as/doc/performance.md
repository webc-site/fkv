# কাৰ্যক্ষমতা

`fkv_bench` এটা নিৰ্দিষ্ট চাবি স্থানত লিখা, পঢ়া, আৰু স্কেন লোডসমূহ পৰীক্ষা কৰক।

```bash
cargo run --release -p fkv_bench -- \
  --workload write-read --rows 20000 --batch-size 100
```

সূচকসমূহৰ ভিতৰত থ্ৰুপুট, প্ৰতিটো পৰ্যায়ত বিলম্ব, আৰু শীৰ্ষ RSS অন্তৰ্ভুক্ত। মুক্তি কাৰ্য্যপ্ৰবাহ মুক্তি x86_64 /
`fkv_bench` aarch64 ৰ বাবে বাইনাৰী।

## RocksDB/fjall ৰ সৈতে তিনিমুখীয়া মেচআপ

`crate/perf/fkv_compare` একেটা ষ্টেজ ড্ৰাইভাৰ আৰু একেটা কি এনকোডিং ব্যৱহাৰ কৰক (শেষত 8-বাইট বিগ-এণ্ডিয়ান চাবস্ক্রিপ্ট,
অভিধানৰ ক্ৰম চাবস্ক্রিপ্ট ক্ৰমৰ সৈতে সামঞ্জস্যপূৰ্ণ) fkv, RocksDB, fjall পৰীক্ষা কৰক: RocksDB উত্তীৰ্ণ হৈছে
`crate/perf/fkv_compare/cpp/rocksdb_ffi.cpp` কমপাইল কৰা অংশীদাৰী লাইব্ৰেৰী dlopen (একে C.) ৰ সৈতে লোড কৰা হৈছে
ABI, Rust বিল্ডে RocksDB ৰ সৈতে সংযোগ নকৰে), fjall এ `fjall 3` প্ৰত্যক্ষভাৱে ব্যৱহাৰ কৰে। তিনিটা ইঞ্জিনৰ প্ৰত্যেকেই এটা লাইব্ৰেৰী খোলে।
একেটা লাইব্ৰেৰীত পৰ্যায়ৰ ক্ৰমত আগবাঢ়ি যাওক: বাল্ক লোডে তথ্য সৃষ্টি কৰে, আৰু তাৰ পিছত len / পইণ্ট পঢ়া / পৰিসীমা পঢ়া /
ডিলিচনে সকলোৱে একে তথ্যক প্ৰভাৱিত কৰে।

```bash
cargo build --release -p fkv_compare
bash scripts/perf/build_rocksdb_ffi.sh # তৃতীয় স্তম্ভ এৰি দিয়ক যদি RocksDB নাই
./target/release/fkv_compare \
  --rows 25000000 --bulk-rows 25000000 --cache-bytes 268435456 \
  --readers 1,4,8,16,32 --workdir /tmp/fkv-compare \
  --rocksdb-lib target/perf/librocksdb_bench_ffi.so \
  --json /tmp/fkv-compare.json
```

হোমপেজ মেট্ৰিক্সৰ বাবে সংখ্যাসমূহ কেৱল এটা অনুসৰণযোগ্য ৰানৰ পৰাহে আহিব পাৰে:

```bash
python3 scripts/perf/fkv_compare_to_js.py \
  --json /tmp/fkv-compare.json --perf-js web/src/conf/perf.js \
  --মেচিন "..." --উৎস "CI চলাওক <id>"
```

GitHub Actions' `perf.yml` এ ঠিক এই কাম কৰে (`librocksdb-dev` সংস্থাপন কৰক, প্ৰগ্ৰাম এডাপ্টাৰসমূহ, চলাওক
25M শাৰী মেট্ৰিক্স, আৰ্টিফেক্ট আপলোড কৰক, আৰু পৃষ্ঠাটো প্ৰত্যক্ষভাৱে বেকফিল কৰক যেতিয়া `backfill=true`)।

### কেলিবাৰ

- **ডাটা/কেচ অনুপাত**: ২৫,০০০,০০০ শাৰী × ১১৬ বি ≈ ২৭৬৬ মিবি ডাটা, প্ৰতিটো ইঞ্জিনত ২৫৬ মিবি কেচ,
  ≈ 11:1, RocksDB ৰ 97 GiB ডাটা/6 GiB কেচৰ অফিচিয়েল পৰ্যালোচনাৰ সৈতে প্ৰান্তিককৃত (≈ 16:1)।
- **কেশ্বৰ একে পৰিমাণ**: fkv ৰ পৃষ্ঠা কেচ (সূচী/ডাটা একে পুল), RocksDB ৰ ব্লক কেশ্ব
  (`cache_index_and_filter_blocks=true`, ব্লকৰ আকাৰ 4 KiB), fjall ৰ নিজৰ ব্লক কেশ্ব
  বাজেটসমূহ সকলো একে সংখ্যক বাইটলৈ সংহতি কৰা হৈছে।
- **স্থায়িত্ব কেলিবাৰ (তুলনা স্তম্ভই RocksDB অবিকল্পিত বিন্যাস ব্যৱহাৰ কৰে, প্ৰান্তিককৰণ অবিহনে)**: fkv 1×তথ্য পৃষ্ঠা + প্ৰতি বেচত
  1×manifest `fdatasync` (C++ EloqStore ৰ SyncData + AppendManifest লৈ সমৰূপী,
  দুয়োটাৰে কোনো অফ চুইচ নাই); RocksDB স্তম্ভই **অবিকল্পিত বিন্যাস** ব্যৱহাৰ কৰে (WAL অন, `WriteOptions.sync=false`,
  কোনো ক্ৰমিক fsync নাই), fjall এ অবিকল্পিত (`PersistMode::Buffer`)ও ব্যৱহাৰ কৰে। সেয়েহে লিখাৰ পৰ্যায় (একক লিখা /
  বেচ লিখাৰ মাজৰ পাৰ্থক্য) হৈছে **স্থায়িত্ব শক্তিৰ পাৰ্থক্য**, প্ৰণয়নৰ পাৰ্থক্য নহয়, যিটো সংখ্যাৰ সৈতে পৃষ্ঠাত উল্লেখ কৰিব লাগিব।
  যদি আপুনি "একে সমন্বয় শক্তিৰ অধীনত কোন দ্ৰুত" বিশ্লেষণ কৰিব বিচাৰে, `--align-fsync` যোগ কৰক (sync=true ৰ সৈতে RocksDB খোলক,
  fjall এ SyncAll ব্যৱহাৰ কৰে), এই বিকল্প বাহ্যিকভাৱে প্ৰকাশিত মেট্ৰিচসমূহৰ বাবে ব্যৱহাৰ কৰা নহয়।
- **দুটা fkv ড্ৰাইভাৰ**: `--fkv-driver store` (অবিকল্পিত, প্ৰক্ৰিয়াৰ ভিতৰত এটা `Store` ৰ সৈতে প্ৰত্যক্ষভাৱে সংযুক্ত, আৰু
  RocksDB / fjall লাইব্ৰেৰী কল) আৰু `--fkv-driver runtime` (মোতায়েন ধৰণ: এটা প্ৰক্ৰিয়াও
  `--fkv-shards` শ্বাৰ্ড থ্ৰেডসমূহ, অনুৰোধসমূহ চাবিৰ দ্বাৰা ৰাউট কৰা হয়, C++ EloqStore ৰ ৰাজহুৱা পঢ়া আৰু লিখাৰ সৈতে প্ৰান্তিককৃত
  আন্তঃপৃষ্ঠ)। পিছৰটোৰ প্ৰতিটো অনুৰোধ শাৰীৰ মাজেৰে যাব লাগিব + ক্ৰছ-থ্ৰেড ৱেক-আপ, স্থানীয় (macOS, ফাইল IO থ্ৰেড পুলৰ মাজেৰে যায়)
  পঢ়াৰ সময় প্ৰায় ২০ μs/সময়, যিটো প্ৰক্ৰিয়াৰ ভিতৰত প্ৰত্যক্ষ সংযোগতকৈ এক ক্ৰমৰ লেহেমীয়া; Linux/io_uring ত বহুত কম খৰচী, কিন্তু
  এতিয়াও এটা জাঁপ। পৃষ্ঠা মেট্ৰিক্সে ষ্ট'ৰ কেলিবাৰ ব্যৱহাৰ কৰে, আৰু চলনসময় কেলিবাৰ "ডিপ্লয়মেন্ট ফৰ্ম বনাম C++" ৰ বাবে ব্যৱহাৰ কৰা হয়
  "ৰাজহুৱা আন্তঃপৃষ্ঠ"ৰ তুলনা (fkv চলনসময় একক-থ্ৰেড পঢ়া প্ৰায় 50 kops/s, C++ EloqStore FFI একক-থ্ৰেড
  শ্বাৰ্ড প্ৰায় ২১ কপছ/ছেকেণ্ড)।
- **সমকালীনতা কেলিবাৰ পঢ়ক**: fkv কাষৰ থ্ৰেড সংখ্যা = `min(readers, --read-max-concurrency)`, অবিকল্পিত
  ওপৰৰ সীমা 4 (মূল্যায়ন যন্ত্ৰ vCPU ৰ সৈতে প্ৰান্তিককৃত), **নহয়** "প্ৰতি পাঠকৰ বাবে এটা থ্ৰেড" - অতিক্ৰম কৰা স্তৰে কেৱল শাৰী বৃদ্ধি কৰে;
  প্ৰতি থ্ৰেডত কেশ্ব = 256 MiB / থ্ৰেডৰ সংখ্যা (মুঠ পৰিমাণ নিৰ্দিষ্ট কৰা হৈছে, পাঠকৰ সৈতে টুকুৰা কৰা হোৱা নাই), আৰু ব্যৱহাৰ কৰা হৈছে
  `FuturesUnordered` `--read-window` (অবিকল্পিত ১৬) অনুৰোধসমূহ উৰি যাওক। RocksDB ফালে আছে
  `readers` প্ৰতিটো `std::thread` একেলগে পঢ়ে; fjall ফালে একক-থ্ৰেডযুক্ত লুপ (পাঠকৰ গিয়াৰক আওকাণ কৰি,
  কেৱল এটা প্ৰসংগ স্তম্ভ হিচাপে)। `--no-fkv-read-threads` এ "এটা চলনসময়ত ইন্টাৰলিভ কৰা N এচিনক্ৰ'নাছ শৃংখল" লৈ পুনৰ অৱক্ষয় হ'ব পাৰে।
  সেইটো পাইপলাইনৰ গভীৰতা, সমকালীনতা নহয়, আৰু ইঞ্জিনৰ মাজত তুলনাযোগ্য নহয়।
- **len()**: তিনিটা ইঞ্জিনৰ কোনো এটাতে O(1) গণনা আন্তঃপৃষ্ঠ নাই। এই শাৰীটো সম্পূৰ্ণ টেবুল গণনাৰ হাৰ, O(1) লুকআপ নহয়।
