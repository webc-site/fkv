# Απόδοση

`fkv_bench` Δοκιμάστε την εγγραφή, την ανάγνωση και τη σάρωση φορτίων σε ένα σταθερό χώρο κλειδιού.

```bash
cargo run --release -p fkv_bench -- \
  --workload write-read --rows 20000 --batch-size 100
```

Οι δείκτες περιλαμβάνουν τη διεκπεραίωση, την καθυστέρηση σε κάθε στάδιο και το μέγιστο RSS. απελευθέρωση ροής εργασίας απελευθέρωση x86_64 /
`fkv_bench` δυαδικό για aarch64.

## Τριμερής αντιστοίχιση με RocksDB/fjall

`crate/perf/fkv_compare` Χρησιμοποιήστε το ίδιο πρόγραμμα οδήγησης σκηνής και την ίδια κωδικοποίηση κλειδιού (8-byte μεγάλος δείκτης endian στο τέλος,
Η σειρά του λεξικού είναι συνεπής με τη σειρά υπογραφής) Δοκιμή fkv, RocksDB, fjall: Το RocksDB πέρασε
`crate/perf/fkv_compare/cpp/rocksdb_ffi.cpp` Η μεταγλωττισμένη κοινόχρηστη βιβλιοθήκη φορτώνεται με dlopen (το ίδιο C
Το ABI, το Rust build δεν συνδέεται με το RocksDB), το fjall χρησιμοποιεί απευθείας το `fjall 3`. Κάθε μία από τις τρεις μηχανές ανοίγει μια βιβλιοθήκη.
Προχωρήστε στην ίδια βιβλιοθήκη με τη σειρά των σταδίων: η μαζική φόρτωση δημιουργεί δεδομένα και, στη συνέχεια, len / point reading / range reading /
Όλες οι διαγραφές επηρεάζουν τα ίδια δεδομένα.

```bash
cargo build --release -p fkv_compare
bash scripts/perf/build_rocksdb_ffi.sh # Παράβλεψη της τρίτης στήλης εάν δεν υπάρχει RocksDB
./target/release/fkv_compare \
  --rows 25000000 --bulk-rows 25000000 --cache-bytes 268435456 \
  --readers 1,4,8,16,32 --workdir /tmp/fkv-compare \
  --rocksdb-lib target/perf/librocksdb_bench_ffi.so \
  --json /tmp/fkv-compare.json
```

Οι αριθμοί για τον πίνακα αρχικής σελίδας μπορούν να προέρχονται μόνο από μία ανιχνεύσιμη εκτέλεση:

```bash
python3 scripts/perf/fkv_compare_to_js.py \
  --json /tmp/fkv-compare.json --perf-js web/src/conf/perf.js \
  --machine "..." --πηγή "CI run <id>"
```

Το `perf.yml` του GitHub Actions κάνει ακριβώς αυτό (εγκατάσταση `librocksdb-dev`, προσαρμογείς προγράμματος, εκτέλεση
Πίνακας γραμμών 25 εκατομμυρίων, μεταφορτώστε το τεχνούργημα και συμπληρώστε απευθείας τη σελίδα όταν `backfill=true`).

### διαμέτρημα

- **Λόγος δεδομένων/κνήμης**: 25.000.000 σειρές × 116 B ≈ 2766 MiB δεδομένων, 256 MiB κρυφής μνήμης ανά μηχανή,
  ≈ 11:1, ευθυγραμμισμένο με την επίσημη κριτική του RocksDB για δεδομένα 97 GiB/6 GiB cache (≈ 16:1).
- **Ίδιος αριθμός κρυφής μνήμης**: προσωρινή μνήμη σελίδων του fkv (ίδια ομάδα ευρετηρίου/δεδομένων), μπλοκ προσωρινής μνήμης του RocksDB
  (`cache_index_and_filter_blocks=true`, μέγεθος μπλοκ 4 KiB), η κρυφή μνήμη μπλοκ του ίδιου του fjall
  Όλοι οι προϋπολογισμοί ορίζονται στον ίδιο αριθμό byte.
- **Διαμέτρημα εμμονής (η στήλη σύγκρισης χρησιμοποιεί την προεπιλεγμένη διαμόρφωση του RocksDB, χωρίς στοίχιση)**: fkv 1×σελίδα δεδομένων + ανά παρτίδα
  1×manifest `fdatasync` (Isomorphic to SyncData + AppendManifest του C++ EloqStore,
  Κανένα από τα δύο δεν έχει διακόπτη απενεργοποίησης). η στήλη RocksDB χρησιμοποιεί την **προεπιλεγμένη διαμόρφωση** (WAL on, `WriteOptions.sync=false`,
  Χωρίς διαδοχικό fsync), το fjall χρησιμοποιεί επίσης την προεπιλογή (`PersistMode::Buffer`). Επομένως η φάση εγγραφής (μονή εγγραφή /
  Η διαφορά μεταξύ των εγγραφών παρτίδας) είναι η **διαφορά αντοχής επίμονης**, όχι η διαφορά υλοποίησης, η οποία πρέπει να αναφέρεται στη σελίδα μαζί με τον αριθμό.
  Εάν θέλετε να αναλύσετε "ποιος είναι πιο γρήγορος με την ίδια ισχύ συγχρονισμού", προσθέστε `--align-fsync` (ανοίξτε το RocksDB με sync=true,
  Το fjall χρησιμοποιεί το SyncAll), αυτή η επιλογή δεν χρησιμοποιείται για εξωτερικά δημοσιευμένους πίνακες.
- **Δύο προγράμματα οδήγησης fkv**: `--fkv-driver store` (προεπιλογή, απευθείας συνδεδεμένο σε ένα μόνο `Store` εντός της διαδικασίας και
  Το RocksDB / fjall είναι επίσης κλήσεις βιβλιοθήκης) και `--fkv-driver runtime` (λειτουργία ανάπτυξης: μια διαδικασία
  `--fkv-shards` θραύσματα νημάτων, τα αιτήματα δρομολογούνται με κλειδί, ευθυγραμμισμένα με δημόσια ανάγνωση και γραφή του C++ EloqStore
  διεπαφή). Κάθε αίτημα του τελευταίου πρέπει να περνάει από την ουρά + αφύπνιση μεταξύ νημάτων, εγγενές (macOS, το αρχείο IO περνά μέσα από το νήμα)
  Ο χρόνος ανάγνωσης είναι περίπου 20 µs/χρόνο, που είναι μια τάξη μεγέθους πιο αργός από την απευθείας σύνδεση κατά τη διαδικασία. πολύ φθηνότερα σε Linux/io_uring, αλλά
  Ακόμα ένα άλμα. Ο πίνακας σελίδων χρησιμοποιεί το διαμέτρημα αποθήκευσης και το διαμέτρημα χρόνου εκτέλεσης χρησιμοποιείται για "φόρμα ανάπτυξης έναντι C++
  Σύγκριση του "Public Interface" (η ανάγνωση ενός νήματος χρόνου εκτέλεσης fkv είναι περίπου 50 kops/s, C++ EloqStore FFI με ένα νήμα
  θραύσμα περίπου 21 κόπς/δευτ.).
- **Διαμέτρημα ταυτόχρονης ανάγνωσης**: fkv πλευρικός αριθμός νήματος = `min(readers, --read-max-concurrency)`, προεπιλογή
  Το ανώτερο όριο είναι 4 (ευθυγραμμισμένο με το μηχάνημα αξιολόγησης vCPU), **όχι** "ένα νήμα ανά αναγνώστη" - το επίπεδο υπέρβασης αυξάνει μόνο την ουρά.
  Προσωρινή μνήμη ανά νήμα = 256 MiB / αριθμός νημάτων (το συνολικό ποσό είναι σταθερό, δεν τεμαχίζεται με αναγνώστες) και χρησιμοποιείται
  `FuturesUnordered` Διατηρήστε τα αιτήματα `--read-window` (προεπιλογή 16) εν κινήσει. Η πλευρά του RocksDB είναι
  `readers` Κάθε `std::thread` διαβάζεται ταυτόχρονα. βρόχος μονής κλωστής στην πλευρά fjall (αγνοώντας τον εξοπλισμό του αναγνώστη,
  Μόνο ως στήλη αναφοράς). Το `--no-fkv-read-threads` μπορεί να εκφυλιστεί ξανά σε "διαπλεκόμενες N ασύγχρονες αλυσίδες σε ένα μόνο χρόνο εκτέλεσης".
  Αυτό είναι το βάθος του αγωγού, όχι η ταυτόχρονη, και δεν είναι συγκρίσιμο μεταξύ των κινητήρων.
- **len()**: Καμία από τις τρεις μηχανές δεν έχει διεπαφές μέτρησης O(1). Αυτή η γραμμή είναι ο ρυθμός καταμέτρησης πλήρους πίνακα, όχι αναζήτηση O(1).
