# Продуктивність

`fkv_bench` Тестове завантаження запису, читання та сканування у фіксованому ключовому просторі.

```bash
cargo run --release -p fkv_bench -- \
  --workload write-read --rows 20000 --batch-size 100
```

Індикатори включають пропускну здатність, затримку на кожному етапі та пік RSS. випуск робочого циклу випуск x86_64 /
`fkv_bench` двійковий файл для aarch64.

## Тристоронній матч із RocksDB/fjall

`crate/perf/fkv_compare` Використовуйте той самий драйвер етапу та те саме кодування ключа (8-байтовий нижній індекс у порядку старшого порядку в кінці,
Порядок словників узгоджується з порядком індексів) Тест fkv, RocksDB, fjall: RocksDB пройдено
`crate/perf/fkv_compare/cpp/rocksdb_ffi.cpp` Скомпільована спільна бібліотека завантажується за допомогою dlopen (той самий C
ABI, збірка Rust не посилається на RocksDB), fjall безпосередньо використовує `fjall 3`. Кожен із трьох механізмів відкриває бібліотеку.
Перехід до тієї самої бібліотеки в порядку етапів: масове завантаження створює дані, а потім len / точкове читання / діапазон читання /
Усі видалення впливають на ті самі дані.

```bash
cargo build --release -p fkv_compare
bash scripts/perf/build_rocksdb_ffi.sh # Пропустити третій стовпець, якщо немає RocksDB
./target/release/fkv_compare \
  --rows 25000000 --bulk-rows 25000000 --cache-bytes 268435456 \
  --readers 1,4,8,16,32 --workdir /tmp/fkv-compare \
  --rocksdb-lib target/perf/librocksdb_bench_ffi.so \
  --json /tmp/fkv-compare.json
```

Числа для матриці домашньої сторінки можуть бути отримані лише з одного відстежуваного прогону:

```bash
python3 scripts/perf/fkv_compare_to_js.py \
  --json /tmp/fkv-compare.json --perf-js web/src/conf/perf.js \
  --machine "..." --source "CI run <id>"
```

`perf.yml` GitHub Actions робить саме це (встановіть `librocksdb-dev`, запрограмуйте адаптери, запустіть
25 млн. матриця рядків, завантажте артефакт і безпосередньо заповніть сторінку, коли `backfill=true`).

### калібр

- **Співвідношення даних/кешу**: 25 000 000 рядків × 116 Б ≈ 2766 МБ даних, 256 МБ кешу на механізм,
  ≈ 11:1, відповідно до офіційного огляду RocksDB щодо 97 ГіБ даних/6 ГіБ кешу (≈ 16:1).
- **Однаковий обсяг кешу**: кеш сторінок fkv (той самий пул індексів/даних), кеш блоків RocksDB
  (`cache_index_and_filter_blocks=true`, розмір блоку 4 КБ), власний кеш блоків fjall
  Усі бюджети мають однакову кількість байтів.
- **Калібр стійкості (стовпець порівняння використовує конфігурацію RocksDB за замовчуванням, без вирівнювання)**: fkv 1×сторінка даних + на пакет
  1×маніфест `fdatasync` (Ізоморфний SyncData + AppendManifest C++ EloqStore,
  Немає вимикача); стовпець RocksDB використовує **конфігурацію за замовчуванням** (WAL увімкнено, `WriteOptions.sync=false`,
  Немає послідовного fsync), fjall також використовує значення за замовчуванням (`PersistMode::Buffer`). Тому фаза запису (один запис /
  Різниця між пакетним записом) полягає в **різниці стійкості**, а не в реалізації, яка має бути вказана на сторінці разом із номером.
  Якщо ви хочете проаналізувати "хто швидший за однакової сили синхронізації", додайте `--align-fsync` (відкрийте RocksDB за допомогою sync=true,
  fjall використовує SyncAll), цей параметр не використовується для зовнішніх опублікованих матриць.
- **Два драйвери fkv**: `--fkv-driver store` (за замовчуванням, безпосередньо підключений до одного `Store` у процесі та
  RocksDB / fjall також є викликами бібліотеки) і `--fkv-driver runtime` (режим розгортання: процес
  `--fkv-shards` сегментованих потоків, запити направляються за ключем, узгоджуються з публічним читанням і записом C++ EloqStore
  інтерфейс). Кожен запит останнього має пройти через чергу + міжпотокове пробудження, нативний (macOS, файл IO проходить через пул потоків)
  Час зчитування становить приблизно 20 мкс/час, що на порядок повільніше, ніж пряме підключення в процесі; набагато дешевше на Linux/io_uring, але
  Ще стрибок. Матриця сторінки використовує калібр магазину, а калібр часу виконання використовується для «форми розгортання проти C++
  Порівняння «Загальнодоступного інтерфейсу» (однопотокове читання під час виконання fkv становить близько 50 коп/с, C++ EloqStore FFI однопотокове
  осколок близько 21 коп/с).
- **Калібр паралельного читання**: номер стороннього потоку fkv = `min(readers, --read-max-concurrency)`, за замовчуванням
  Верхня межа становить 4 (узгоджено з vCPU машини оцінки), **а не** «один потік на зчитувач» — перевищення рівня лише збільшує чергу;
  Кеш на потік = 256 МіБ/кількість потоків (загальний обсяг фіксований, не подрібнюється зчитувачами) і використовується
  `FuturesUnordered` Тримайте `--read-window` (за замовчуванням 16) запитів на льоту. Сторона RocksDB є
  `readers` Кожен `std::thread` читає одночасно; однопотоковий цикл на стороні fjall (ігноруючи спорядження для зчитування,
  Лише як довідковий стовпець). `--no-fkv-read-threads` може повернутися до "перемежованих N асинхронних ланцюжків в одному середовищі виконання".
  Це глибина конвеєра, а не паралелізм, і його неможливо порівняти між механізмами.
- **len()**: жодна з трьох машин не має інтерфейсів підрахунку O(1). Цей рядок є повною швидкістю підрахунку таблиці, а не пошуком O(1).
